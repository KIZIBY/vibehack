# Команда агентов — внутренний гайд

Версия: v1.0

> Разграничение: это ВНУТРЕННИЙ гайд команды агентов (роли, маршрутизация, память, режим задач).
> Контракт УРОВНЯ РЕПО (что можно/нельзя, пред-коммит проверки, публикация) — в корневом `AGENTS.md`
> (открытый стандарт, читается не-Claude тулами). Паспорт проекта (стек, команды, окружения, тестовые
> роли, трекер) — `PROJECT.md`. Начни с них, если работаешь над репо целиком.

Держи этот файл компактным: сюда попадают только подтверждённые cross-agent workflow, команды и уроки,
которые нужны следующему агенту до начала работы.

## Канонические места (Canonical Locations)

- **Каноны ролей** — `agents/roles/<role>.md` (8 ролей, см. «Состав команды»). Канон — единственный
  источник поведения роли.
- **Память ролей** — `agents/memory/<role>.md` (компакт), архив — `agents/memory/archive/<role>/<YYYY-MM>.md`.
  Единственный источник правил памяти (компакт+архив, лимит 1500 строк И ≤60 KB, read-before-run,
  append-only, ротация) — **`docs/guides/MEMORY_CONVENTION.md`**; каноны ссылаются на него, а не
  пересказывают.
- **Runtime-стабы Claude** `.claude/agents/<role>.md` — **тонкие по правилу** (анти-дрейф):
  frontmatter (name/description/tools/model) + обязательная инструкция «прочитай канон
  `agents/roles/<role>.md` целиком». Другие runtime читают канон напрямую или дают эквивалентный
  тонкий адаптер. Полнотекстовые runtime-копии ЗАПРЕЩЕНЫ: они молча дрейфуют и теряют правила канона.
  Поведенческие правки — только в каноне; правки tool surface/модели — только во frontmatter стаба.
- Сейчас у всех 8 ролей есть стабы с тем же id; роль без стаба (например новая) запускается прямым
  чтением канона. При смене tool surface роли правь frontmatter стаба в той же правке — устаревший
  frontmatter может молча лишить браузерную роль headed-браузера и свести её к headless/скриптовому fallback.
- `description` стаба = условие маршрутизации («Use when…», что роль делает и когда её звать), а не
  резюме личности — оркестраторы выбирают исполнителя по этому полю.
- **Claude-специалисты** (`.claude/agents/backend-developer.md`, `frontend-developer.md`, `db-expert.md`,
  `devops-deployer.md`, `ai-engineer.md`, `integration-engineer.md`, `test-runner.md`, `code-reviewer.md`,
  `system-analyst.md`, `hard-critic.md`) — самостоятельные определения узких исполнителей/ревьюеров без
  канона в `agents/roles/`; правило тонкого стаба к ним не относится.
- Периодическая проверка (hygiene-sweep роли `repo-hygiene` + любой агент, правящий каноны): тело
  каждого стаба роли остаётся тонким; если полнотекстовая копия вернулась — сначала перенеси уникальное
  содержимое в канон, затем восстанови стаб.
- Публикация — `docs/guides/GIT_PUBLISH_RUNBOOK.md`.
- Баги — канонический свод `docs/bug-handling-process.md` (intake → diagnose → fix → close + обязательные
  enterprise-правила); bug-hunter mindset — `docs/guides/BUG_HUNTER_RULES.md`. При расхождении свод главнее.
- **Верховный закон проекта — `docs/constitution.md`** (17 инвариантов I-1…I-17; действующая версия
  берётся из заголовка самого файла, а не фиксируется в каноне роли). Любой агент сверяется с ним перед
  действием; precedence при конфликте: `устав > доменный канон > provider-specific adapter (например
  CLAUDE.md) > память`. Этот гайд, `docs/bug-handling-process.md` и `BUG_HUNTER_RULES.md` — подчинённые
  конкретизации устава. Сверка спеки/PR/диффа с инвариантами — `docs/constitution-check.md` (любой
  `MUST-FLAG` = блокер).
- Подтверждённые владельцем правила процесса проекта — `docs/pipeline-rules.md`.
- **Аутентификация продукта** — `docs/guides/AUTH_GUIDE.md` + `PROJECT.md §6`. Обязательна при работе с
  требованиями (спека, трогающая вход/роли/доступ, содержит `## Authentication & Access`), при изменении
  auth-кода и при browser-QA входе (видимая форма входа или документированный тест-байпас, выключенный в
  проде; секреты тестовых пользователей не публикуются — см. «Evidence и правила задач»).

## Команды старта прогона

Определи текущий состав команды до маршрутизации работы:

```bash
find agents -maxdepth 2 -type f -name '*.md' | sort
[ ! -d .claude/agents ] || find .claude/agents -maxdepth 1 -type f -name '*.md' | sort
```

Проверь локальное состояние перед правкой файлов агентов:

```bash
git status --short
```

При правке канона роли, у которой есть стаб, проверь, что стаб остался тонким и указывает на свой канон
(тела намеренно отличаются от канона, поэтому простой `diff` бессмыслен):

```bash
for r in developer repo-hygiene tech-writer visual-qa ux-route-qa workflow-qa chaos-qa regression-qa; do
  f=".claude/agents/$r.md"
  [ -f "$f" ] || continue
  wc -l "$f"                                   # стаб ~30 строк; большое тело = регрессия full-copy
  grep -q "agents/roles/$r.md" "$f" || echo "REGRESSION: $f не указывает на канон"
done
```

Если меняется tool surface / модель — правь frontmatter стаба в той же правке.

## Архитектура и полномочия доставки

- **Лёгкая доставка по умолчанию** не требует Stage 1–4, `Design-Root` или `implementation-start`:
  исполнитель работает в feature-ветке, фиксирует решение соразмерно риску, показывает RED/repro,
  получает GREEN, запускает `bash scripts/check.sh` и открывает PR (merge жмёт человек). Формальный
  `/pipeline` используется для рискованной/регулируемой поставки или по явному выбору владельца.
- В формальном pipeline для нетривиальной фичи/фикса Stage 1–2 строят typed architecture dossier:
  constraints, FR/NFR, не менее трёх кандидатов, hard/soft fitness matrix, минимум две жизнеспособные
  альтернативы либо доказательство `single-feasible-option`, последствия и rollback. Hard violation
  исключает вариант; correctness/data safety/security/compatibility не обмениваются на скорость;
  неразрешимая бизнес-ничья = `NEEDS_ORACLE`. Нетривиальный bugfix использует State V4 `scope=bugfix`
  и те же три roots/quality gates; bug-handling workflow дополняет этот путь, а не обходит его.
- Spec, decisions, traceability и append-only SDD changelog — living design authority Stage 2.
  Discovery на Dev/Quality не прячется в разговоре: design change re-open'ит Stage 2; честное
  `reviewed-no-change` фиксируется в stage-owned delivery/review artifact.
- Любая поведенческая поставка требует execution-grounded RED/repro до изменения, затем GREEN и adjacent
  regression. В формальном pipeline evidence дополнительно bind'ится к pre-implementation content root,
  затем GREEN exact candidate root и adjacent regression. Результаты, вписанные автором в Markdown/TSV
  без runner receipt или воспроизводимого test output, доказательством не являются.
- Только в формальном pipeline до первого RED runtime вызывает `bash scripts/pipeline-state.sh
  implementation-start …`. Он descriptor-preflight'ит templates/targets, batch-создаёт только
  отсутствующие trace/map/test/changelog files, публикует их no-clobber, откатывает только собственные
  inode при отказе и reconciles orphan при retry. Существующие канонические байты и их семантические
  правки не перезаписываются и не auto-stage'ятся.
- Runtime-neutral authority-plane не равен toolchain-neutral execution. V1 допускает direct host
  execution только через `/usr/bin/perl`, `/bin/bash`, `/bin/sh` или repo-local `100755` direct-argv
  wrapper с таким shebang; команды на других toolchain (Python/Node/Go/Java…) оборачиваются в такой
  wrapper и указываются в `PROJECT.md §3`. Явный argv другого toolchain без identity-bound ToolchainRoot
  даёт `CAPABILITY-BLOCKED: execution-toolchain-v1`; ambient `PATH` discovery не является authority.
  Wrapper receipt bind'ит top-level bytes; его transitive exec остаётся trusted declared-code boundary.
  Поведенческие TDD/performance не помечаются `N/A`, а ждут поддержанного execution proof.
- Для рискованных изменений нужен независимый reviewer; в формальном pipeline Stage 4 выполняется
  отдельным reviewer actor/attempt: critical code review проверяет correctness, simplicity/cleanliness,
  maintainability, architecture conformance, security, testability, algorithmic complexity и
  CPU/memory/IO/concurrency/performance. P0/P1/P2 блокируют PASS.
- **UI-impact получает две независимые проверки:** visual-qa — визуал со screenshot+DOM/console/network;
  ux-route-qa — измеренный user journey и quantitative no-regression. Developer screenshot, общий «пакет
  на подпись» или один reviewer за двоих запрещены. Closure требует exact served identity, два разных
  session/actor ID и два разных artifact ID; отсутствие любой оптики запрещает закрытие. Нет
  visible-browser capability — typed `CAPABILITY-BLOCKED` с непокрытой матрицей; static/headless fallback
  остаётся partial evidence. Механическое deploy-bound связывание этой пары не поставлено — обязательность
  держат этот гайд и `docs/pipeline-rules.md`.
- `bash scripts/pipeline-state.sh status <SPEC_DIR>` даёт следующий шаг. Конец batch/context/turn не
  является DONE: оркестратор после каждого batch перечитывает последнюю явную цель, повторно проверяет
  полный scope и продолжает без generic «что дальше?» либо доказывает `DONE | WAIT_OWNER | BLOCKED`.
  Каждый status/final содержит 1–3 ranked advisory recommendations; они не меняют action/scope/authority.

Перед чтением, созданием, комментированием, закрытием или reopen любой задачи прочитай «Режим задач
(ISSUE MODE)» ниже и выполни preflight:

```bash
bash scripts/agent-preflight.sh origin main
```

Если preflight не подтверждает read/write authority активного backend, не заявляй, что действие с задачей
выполнено. Запиши блокер в память роли; переключение на другой backend как runtime-fallback запрещено.

## Режим задач (ISSUE MODE)

Единственный transport-контракт для задач всех ролей. Каноны ролей не содержат transport-команд — они
ссылаются сюда.

**Разрешение backend** (реализуют скрипты `scripts/agent-preflight.sh`, `scripts/intake.sh`,
`scripts/issue-token-lifecycle.pl`; этот раздел их описывает):

1. переменная окружения `ISSUE_BACKEND`, если задана;
2. иначе — первая строка `PROJECT.md`, совпадающая с `^ISSUE_BACKEND=(github|none)\s*$` (`PROJECT.md §7`);
3. иначе — `none`.

Неизвестное значение → fail closed (`BLOCKED: issue-backend-invalid`), без угадывания. Автоматический
fallback, mirror/reconciler и dual-write между режимами запрещены; смена backend — отдельное решение
владельца (правка `PROJECT.md §7`), а не реакция на сбой.

**Авторство.** Каждый новый тикет, комментарий и запись в очереди начинается с `[<роль>]` — `[developer]`,
`[repo-hygiene]`, `[tech-writer]`, `[visual-qa]`, `[ux-route-qa]`, `[workflow-qa]`, `[chaos-qa]`,
`[regression-qa]`. Это **первый авторский токен**; дополнительные теги идут после него. Префикс сохраняет
авторство, когда все агенты пишут из одного аккаунта.

### `ISSUE_BACKEND=github`

Тикеты живут только в GitHub Issues. Репозиторий **всегда** выводится из канонического remote `origin`
(github.com owner/repo); `GH_REPO`, если задан, может только точно повторять его, но не перенаправлять.
Авторизация — штатная `gh auth login`; токены не попадают в репозиторий, argv, логи и тикеты.

Единственный lifecycle (тела передаются через stdin, не через argv):

1. preflight: `bash scripts/agent-preflight.sh origin main`;
2. dedup: `gh issue list --state open --search "<ключевые слова>"` — при совпадении комментируй
   существующий тикет, а не создавай новый;
3. create: `printf '%s' "$BODY" | gh issue create --title "[<роль>] <тема>" --body-file -`;
4. verify-read: `gh issue view <N>` — тикет считается созданным только после него;
5. comment: `printf '%s' "$COMMENT" | gh issue comment <N> --body-file -`, затем `gh issue view <N>`;
6. close + метрика токенов: `perl scripts/issue-token-lifecycle.pl close --ticket <N> --comment "[<роль>] <итог>"`
   — мост сам делает terminal verify-read и только после него пишет resolved-метрику;
7. reopen: `gh issue reopen <N>`, затем `gh issue view <N>`.

Ответ мутации сам по себе не доказательство. Сбой preflight/dedup/мутации/verify-read =
`BLOCKED: issue-backend-unavailable`: успех не имитировать, второй тикет не создавать, в `docs/backlog.md`
как fallback не уходить. Закрытие после правки кода требует published SHA и test evidence. Метки —
только существующие в репозитории; отсутствие подходящей метки не блокирует создание тикета.

### `ISSUE_BACKEND=none`

Внешнего трекера нет. Работа описывается в `specs/` (каталоги спек), очередь задач — `docs/backlog.md`.

- **Тикетные операции пропускаются, а не имитируются.** Агент никогда не пишет «тикет создан/закрыт», не
  выдумывает номера задач и не вызывает `gh issue …` или `issue-token-lifecycle.pl close`. В отчётах —
  честное `issue: N/A (ISSUE_BACKEND=none)` со ссылкой на запись очереди (`B-NNN`) или спеку.
- **Новая находка/задача** → запись `### B-NNN · [<роль>] <тема>` в `docs/backlog.md` по формату, описанному
  в самом файле; перед добавлением — dedup поиском по `docs/backlog.md` и `specs/` (совпало — дополняй
  существующую запись). Тело — тот же обязательный body, который роль положила бы в тикет (секции,
  severity, evidence-ссылки).
- **Комментарий / claim / смена статуса** → новая датированная строка `- YYYY-MM-DD · [<роль>] …` в
  «Журнале» записи (прошлые строки не переписываются) + правка поля «Статус» (`in-progress`, `blocked`…).
- **Закрытие** → статус `done` только после published SHA и того же evidence-gate, что и для тикета (SHA и
  evidence — строкой журнала); `duplicate` / `deferred` / `needs-oracle` — явно, с маршрутом. Reopen — статус
  снова `open` + строка журнала с evidence регрессии.
- Правка `docs/backlog.md` или спеки — обычная правка репозитория: `bash scripts/check.sh`, коммит и
  публикация по `docs/guides/GIT_PUBLISH_RUNBOOK.md`. Если роль не имеет права на публикацию в текущем
  прогоне, находка остаётся в отчёте и памяти роли с пометкой «не внесено в очередь» — это честный gap, не
  успех.

## Публикационная дисциплина

Для любой правки, которая должна попасть в `main`, сначала прочитай `docs/guides/GIT_PUBLISH_RUNBOOK.md`.
Перед коммитом — `bash scripts/check.sh`. Публикация — `bash scripts/agent-publish-main.sh`: на
feature-ветке по умолчанию PR-режим (rebase на `origin/main` → check → push → PR, merge жмёт человек);
на `main` или с `AGENT_PUBLISH_MODE=main` — прямая публикация для solo-проектов; с `PIPELINE_SPEC_DIR`
— строгая exact-OID публикация формального pipeline.

Минимальные общие правила:

- никогда не делать force-push в `main`;
- никогда не откатывать изменения пользователя или других агентов без явного указания;
- не закрывать задачу и не помечать её решённой, пока фикс не опубликован в `origin/main`, remote SHA не
  проверен и (при `github`) комментарий/закрытие с обязательным verify-read не прошли;
- если git-метаданные linked worktree блокируют обычные git-команды, используй штатные скрипты из
  runbook (`scripts/agent-localize-gitdir.sh`), а не импровизированную разрушительную чистку;
- перед удалением worktree — `bash scripts/agent-worktree-memory-check.sh` (незакоммиченная память
  агентов не должна потеряться).

## Состав команды

Роли работают **по запросу** — их вызывает владелец, оркестратор `/pipeline` или другая роль. Расписаний
и фоновых запусков в харнессе нет.

| Роль | Канон | Claude-стаб | Звать, когда |
|---|---|---|---|
| `developer` | `agents/roles/developer.md` | `.claude/agents/developer.md` | Нужно закрыть задачу/баг, не требующий решения владельца: триаж → State V4/TDD → проверки → публикация → верифицированное закрытие. |
| `repo-hygiene` | `agents/roles/repo-hygiene.md` | `.claude/agents/repo-hygiene.md` | Разрослись ветки/worktree/PR/stash, грязный `main`, нужна ротация памяти, проверка стабов или чистка корня репо. |
| `tech-writer` | `agents/roles/tech-writer.md` | `.claude/agents/tech-writer.md` | Нужна/устарела документация, справка, ролевые гайды, формулировки для product oracle; куратор этого гайда; скан свежести docs. |
| `visual-qa` | `agents/roles/visual-qa.md` | `.claude/agents/visual-qa.md` | Визуальный аудит UI по 8 оптикам (+9-я «пересечения»); независимый visual-receipt для закрытия UI-impact. Только смотрит, код не правит. |
| `ux-route-qa` | `agents/roles/ux-route-qa.md` | `.claude/agents/ux-route-qa.md` | Замер стоимости пользовательского маршрута (KLM-GOMS), продуктовая карта и «что урезать»; независимый journey/no-regression receipt для UI-impact. |
| `workflow-qa` | `agents/roles/workflow-qa.md` | `.claude/agents/workflow-qa.md` | Исчерпывающий browser-only QA критических workflow: целостность данных между видами, around-bug регрессия, ретест фиксов. |
| `chaos-qa` | `agents/roles/chaos-qa.md` | `.claude/agents/chaos-qa.md` | Широкий adversarial QA-прогон: оркестрирует независимые группы-персоны (новичок, злоумышленник по правам, перегруз, плохая сеть, мобильный…), требует evidence от каждой. |
| `regression-qa` | `agents/roles/regression-qa.md` | `.claude/agents/regression-qa.md` | Полный прогон e2e-регрессии проекта, триаж падений (продукт / тест / окружение), ведение задач по падениям, ревалидация «починенного». |

Нет пользовательского UI (`PROJECT.md §8`) → `visual-qa`, `ux-route-qa`, `workflow-qa` = N/A.

| `hard-critic` | Оспорить допущения, найти альтернативы, остановить over-engineering до реализации. |

## Маршрутизация

| Что нашли / что нужно | Куда |
|---|---|
| Баг или задача без решения владельца | `developer` (или узкий специалист, если правка целиком в его области) |
| Нужно продуктовое решение / спорный приоритет | владелец: `NEEDS_ORACLE` с конкретным вопросом, работа не берётся |
| Серверная/API/авторизационная регрессия | `Suggested agent route: backend-developer` |
| Дефект UI-компонента/формы/маршрута | `Suggested agent route: frontend-developer` |
| Миграция/схема/SQL/гонки данных | `Suggested agent route: db-expert` |
| Стенд недоступен, деплой/откат сломан | `Suggested agent route: devops-deployer` |
| Пробел или устаревание документации | `tech-writer` |
| Грязный `main`, ветки/worktree, ротация памяти | `repo-hygiene` |
| Закрытие user-visible фикса | `workflow-qa` (функционально) + для UI-impact отдельные `visual-qa` и `ux-route-qa` на одной served identity + при наличии e2e — `regression-qa` |
| Широкий pre-release аудит качества | `chaos-qa` (сама выбирает группы) |
| Независимый review изменения | `code-reviewer`, для архитектурных развилок — `system-analyst` + `hard-critic` |

Правила маршрутизации:

- В тикете/записи очереди роль указывает `Suggested agent route: <id>`, если подходящий исполнитель есть.
- QA-роли находят, `developer` и специалисты чинят. QA-роль не подписывает чужой verdict и не заменяет
  другую оптику: функциональный (`workflow-qa`), визуальный (`visual-qa`) и маршрутный (`ux-route-qa`)
  receipt — три разные сессии.
- **Маршрут к роли, которую сейчас никто не запускает, не выполняется молча.** Оркестратор либо явно
  запускает прогон этой роли (по её канону), либо задача остаётся у инициатора/уходит запущенной роли, а
  факт фиксируется в задаче и памяти. «Отправил и забыл» = задача потеряна.
- Роль, передавшая работу другой роли, не закрывает свою итерацию до подтверждения от целевой роли (или
  явно фиксирует открытый хвост в отчёте и памяти).
- Если ни одна роль не подходит — оставь задачу обычным элементом бэклога и объясни недостающий маршрут
  в задаче или памяти.

## Индекс памяти

- Память роли — `agents/memory/<role>.md`. **Файл создаёт сама роль при первом прогоне** по шаблону из
  `docs/guides/MEMORY_CONVENTION.md`; до первого прогона его отсутствие — норма, а не фантомная ссылка.
- Статичной таблицы статусов здесь нет: дата последнего прогона роли — `git log -1 --format=%as --
  agents/memory/<role>.md`, размер компакта — `wc -l -c agents/memory/*.md`, история — журнал прогонов в
  самом файле. Лимиты и ротация — `docs/guides/MEMORY_CONVENTION.md`; backstop-ротация — hygiene-sweep
  роли `repo-hygiene`.
- Память пишется в том checkout/worktree, где идёт прогон. Перед удалением worktree обязателен детектор
  `bash scripts/agent-worktree-memory-check.sh` (exit 1 = незакоммиченная память найдена; перенеси её
  append-only в канонический файл до удаления).

## Границы продуктовой работы

- Браузерные QA-роли работают с продуктом через видимый браузер как реальный пользователь. Headless,
  прямой API, SQL, curl, backend CLI и скрытые endpoint'ы не являются evidence продуктовой работы (кроме
  явно разрешённых каноном in-browser проб, например enforcement-проба `visual-qa`).
- Административные операции продукта (пользователи, роли, права, настройки) агенты выполняют через UI
  продукта под тестовой ролью из `PROJECT.md §5`. Разовый bootstrap учётки вне UI допустим только как
  задокументированное исключение владельца; рутинная админ-работа UI не обходит.
- `workflow-qa` обязана снимать скриншоты, ошибки консоли, сетевые сбои, проверять сохранность после
  перезагрузки, адаптивность и заполнять visual scorecard.
- Для cookie-аутентификации вход выполняется через видимую форму. Вброс токенов в `sessionStorage` не
  является валидным evidence, если в сессии участвуют httpOnly refresh-cookies.
- Параллельные браузерные QA-роли или группы не делят одну браузерную сессию/вкладку. Отдельный headed
  профиль/userDataDir — только если runtime это позволяет, иначе прогоны идут последовательно; если
  навигацию, cookies, скриншоты или snapshot'ы перехватили — прогон помечается blocked/degraded, а
  static-only, headless, in-page fetch или общая вкладка не становятся финальным evidence.
- Объявленные в профиле браузерные инструменты не доказывают, что под-агенты получили capability. Если у
  порождённых QA-под-агентов нет видимого браузера — их группы blocked/degraded; браузерный fallback
  только у оркестратора — partial evidence с перечнем непокрытых групп.
- `visual-qa` — только визуал: findings со скриншотами и маршрутизация. Не сохраняет, не отправляет, не
  удаляет реальные данные и не правит компоненты (мутации — только на одноразовых сущностях своего прогона).
- Мобильное/адаптивное evidence требует проверенных размеров viewport, а не успешного вызова resize.
  CSS-clamp или JS-подмена viewport могут подтвердить видимый дефект, но это partial evidence; если
  настоящая эмуляция mobile/tablet/desktop недоступна — прогон degraded, мобильное покрытие не заявляется.
  Headed-браузер подключается штатной capability активного runtime (`PROJECT.md §8`; для Claude, например,
  Playwright MCP) — это пример, а не зависимость харнесса.
- Полное evidence `regression-qa` = полный прогон e2e-сьюта проекта (`PROJECT.md §3`) с учётом
  failed/flaky/skipped; quick/focused/unit/разовые live-проверки — диагностика, а не полный прогон.
- Роли, не являющиеся продуктовыми операторами, не мутируют продуктовые данные, если их канон явно этого
  не разрешает. Одноразовые тестовые сущности помечаются префиксом `QA-<роль>-<YYYYMMDD>` и убираются
  после проверки.

## Evidence и правила задач

- Новую задачу создавай только после поиска совпадающей открытой (тикет или запись очереди); если одну
  проблему уже покрывают несколько открытых задач — обнови каноническую и маршрутизируй dedup/закрытие
  остальных, а не заводи ещё одну.
- Действие с задачей засчитывается только после успешного ответа backend и обязательного verify-read из
  ISSUE MODE; сбой transport никогда не разрешает повтор через другой backend.
- Не добавляй дублирующих комментариев в тот же день, если evidence и состояние решения не изменились —
  зафиксируй no-op в памяти.
- Авторство — `[<роль>]` первым токеном (см. ISSUE MODE).
- Для заявлений о визуальном обрезании/усечении подкрепляй скриншот DOM-измерениями (`scrollWidth` vs
  `clientWidth`), если возможны артефакты рендера/сжатия; если DOM опровергает обрезание — исправь
  finding, а не держи ложный визуальный баг.
- При разборе старого бэклога или кластера сначала проверь текущее состояние live/кода. Каждую задачу
  закрывай с конкретным сопоставлением: тот же кластерный фикс, свежее подтверждённое решение,
  канонический дубликат или явный defer с владельцем/причиной; никаких общих bulk-close комментариев.
- Не закрывай и не «цепочно верифицируй» соседние задачи по общему симптому. Нужны тот же reproducer и тот
  же путь фикса; иначе задача остаётся открытой или переоткрывается с более узкой первопричиной.
- Закрытие фикса требует published SHA/deploy/test evidence. Если задача закрыта как дубликат, отложена
  или `NEEDS_ORACLE` — скажи это явно с маршрутом или следующим владельцем и не называй её
  исправленной/задеплоенной.
- Пароли, токены, cookies, session ID и полные auth-заголовки не попадают в память, скриншоты для общего
  доступа, отчёты, тикеты и очередь.
- Артефакты сессии (QA-отчёты, snapshot'ы страниц, JSON/PNG-дампы проб, статус-заметки) никогда не лежат
  в корне репозитория: evidence — в `docs/audit-evidence/<YYYY-MM-DD>/<роль>/…` (каталог создаётся по
  необходимости). В git-worktree-сессии browser capability может разрешать относительные пути внутри
  активного worktree, а не основного checkout — сначала получи корень через
  `git rev-parse --show-toplevel` и создавай каталог evidence именно там, иначе скриншоты «теряются».
  `scripts/agent-preflight.sh` предупреждает о нарушениях чистоты корня.
- Если поведение UI противоречит документации — это риск docs/продукта до свежего evidence или решения
  product oracle.
- Неоднозначный факт маршрутизируй нужной роли или запиши в память своей роли как открытый вопрос; не
  возводи его в политику этого гайда.

## Подтверждённые уроки QA

- На ЛЮБОЙ баг ЛЮБОЙ критичности (P0–P3): полный systematic root-cause workflow (воспроизвести →
  изолировать → сформулировать фальсифицируемую гипотезу → доказать) ДО фикса; патч по симптому — не фикс.
  Если runtime даёт skill `superpowers:systematic-debugging`, это optional UX-адаптер; его отсутствие
  workflow не отменяет. См. `docs/bug-handling-process.md`.
- Никаких placeholder-реализаций: полная реализация или честный blocker/`NEEDS_ORACLE` — «заглушка, чтобы
  собралось» нарушает I-11. Перед выводом «не реализовано» проведи независимые проходы чтения/поиска (один
  пустой grep — не доказательство). Параллельная делегация — только если runtime её даёт; иначе проходы
  последовательно в свежих контекстах с явной пометкой `degraded-concurrency`.
- Гигиена контекста делегирования: от каждого делегированного прохода наверх возвращается ТОЛЬКО summary
  (результат, файлы, статус), не транскрипт; fan-out допустим для чтения/поиска, build/test — один процесс
  за раз. Context rot и context poisoning лечатся свежими контекстами и явными handoff'ами через
  state-файлы независимо от наличия subagent API.
- Context/token evidence: при наличии точного usage провайдера каждая попытка задачи записывается через
  `scripts/context-budget.pl record-usage` либо `ingest-jsonl`, а проверенно опубликованная задача — через
  `resolve`. Без точного usage запись пропускается, а не оценивается по числу сообщений. `check` сравнивает
  только сопоставимые когорты `class × runtime × model`; RED — сигнал расследовать рост, не повод прятать
  дорогие попытки.
- Enterprise-планка: никаких тихих заплаток. Лечится первопричина; workaround — только явно помеченный
  временный (`// TEMP: ... see <задача>`) со ссылкой на задачу системного фикса.
- Scope-the-class: спроси, может ли баг повториться в другом месте; если да — чини каждую ось (роль /
  членство / состояние / поверхность), а не только репортнутую, и ставь guard от регрессии.
- Фикс не ухудшает архитектуру / производительность / безопасность: предикаты доступа внутри единого
  запроса, без N+1, паритет авторизационного резолвера и enforcement, fail-closed доступ, 404-oracle для
  чужих ресурсов, никаких утечек секретов.
- Zero-trust: ошибаться может каждый — репортёр, `developer` и его «FIXED», зелёный CI, твоя собственная
  память. Результат принимается только с воспроизводимым evidence, полученным и осмотренным лично, лучше на
  другой оси, чем источник заявления. Доверие — дефект процесса.
- Заявления `FIXED` не принимаются без свежей ревалидации на безопасных/одноразовых данных.
- Для прямого доступа по ID и межтенантных поверхностей проверяй все три пункта: отказ на чтение, отказ на
  мутацию, неизменность состояния, видимого владельцу.
- Дочерним ресурсам и экспортам нужна собственная проверка видимости родителя; защищённая detail-ручка
  родителя не доказывает безопасность вложений, файлов, версий, экспортов и lifecycle-мутаций.
- Дочерние write-ручки проверяют видимость родителя ДО валидации тела запроса; поведение на кривом payload
  не должно становиться oracle скрытых ID.
- Feature-флаги, смоделированные как права, должны доказывать наличие включённой области; общий
  админ-обход недостаточен.
- Прерванный полный прогон `regression-qa` не заменяет последний завершённый чистый baseline: фиксируется
  причина прерывания, завершённые тесты — только partial evidence.
- Чистый полный e2e-прогон — канал негативного сигнала для покрытых сьютом сценариев, а не closure-gate
  для находок других QA-ролей вне сьюта.
- После фиксов продуктового/API-контракта сначала проверь соответствующие pinned/регрессионные тесты:
  устаревшие assertion'ы маскируются под регрессию «FIXED».
- Закрытие user-visible фикса требует широкого evidence `regression-qa` (если есть e2e-сьют),
  функционального браузерного evidence `workflow-qa` и для UI-impact — отдельных сессий `visual-qa` и
  `ux-route-qa` на exact served identity. Нет headed-браузера — `CAPABILITY-BLOCKED`, а не закрытие
  follow-up'ом. Точечный ретест двух багов недостаточен.
- Фикс санитизации пользовательского контента одного поля неполон, пока не проверены соседние поля с
  пользовательским контентом и рендереры экспорта (или явно не выведены из скоупа); зачистка persisted-XSS
  требует ещё и DOM-evidence в браузере для видимых пользователю поверхностей.

## Правка этого файла

- Куратор — `tech-writer`. Изменения минимальные и опираются на памяти ролей, каноны, runbook'и,
  опубликованные задачи или свежее evidence.
- Не копируй сюда длинные ролевые матрицы — они живут в канонах.
- Перед применением старых отсоединённых патчей docs/evidence сравни их с текущим `origin/main`; не
  регрессируй более новые проверенные факты.
- Если evidence слишком тонкое — оставь заметку в памяти своей роли как открытый вопрос, а не правило здесь.
