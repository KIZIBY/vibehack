# Разработка самого харнесса

Этот файл — про изменения в репозитории харнесса (правила, каноны, скрипты, тесты). Как
пользоваться харнессом в проекте — [README.md](README.md); как устроены тесты — [TESTING.md](TESTING.md).

Весь процесс — одна прямая линия: **понял задачу → ветка → изменение → RED/GREEN → self-test →
PR → merge человеком**.

## Один раз на клон

```bash
git clone <URL репозитория харнесса>
cd <каталог клона>
bash scripts/install-git-hooks.sh     # pre-commit: append-only журналы, секреты, TODO без тикета
```

## Цикл

### 1. Ответвись от main

```bash
git checkout main && git pull
git checkout -b feature/<кратко>        # или fix/…, docs/…, chore/…
```

### 2. Сначала RED

Поведенческое изменение (скрипт, гейт state-машины, линт, хук) начинается с падающего теста:
новый или изменённый кейс в `tests/harness/cases/`, который падает **по ожидаемой причине** на
текущем коде. Ошибка окружения/синтаксиса RED-ом не считается. Новый кейс регистрируется строкой в
`tests/harness/tiers.tsv` (уровень, `min-asserts`, опциональный потолок в секундах) — подробности
в [TESTING.md](TESTING.md).

Правка только текста доктрины без смены поведения теста не требует, но конвенция, которая что-то
обязывает, должна получить исполняемый путь (тест, линт, guard) — инвариант I-17 устава
(`docs/constitution.md`).

### 3. Изменение → GREEN

```bash
bash tests/harness/run-tests.sh <CASE>          # твой кейс
bash tests/harness/run-tests.sh --tier fast     # быстрый набор во время работы
bash tests/harness/run-tests.sh                 # полный self-test перед публикацией — 0 FAIL
```

Если правка влияет на способность агентов решать задачи (каноны, команды, pipeline-скрипты), прогони
`bash scripts/agent-eval.sh` до и после и приложи Δ `% Resolved` к PR.

### 4. Коммиты

`feat|fix|docs|chore(scope): краткое описание` — по образцам `git log`. Pre-commit сам скажет,
если что-то не так (секрет, переписанная строка журнала).

### 5. Подготовь PR

```bash
bash scripts/agent-publish-main.sh
```

Скрипт на feature-ветке: проверит чистоту дерева → заберёт свежий `origin/main` → перенесёт твои
коммиты (`rebase`) → прогонит `scripts/check.sh` на перенесённом результате → запушит ветку
(`--force-with-lease`) и подскажет, как открыть PR. Пока ты ждал ревью, main ушёл вперёд — просто
повтори этот шаг.

### 6. Merge

Ревью и merge делает человек. Слияние — fast-forward/rebase: история остаётся прямой (merge-коммиты
ломают exact-OID публикацию формального pipeline).

## Правила

- **`main` закрыт для прямых push** — вход только через PR с зелёным self-test.
- **Данные append-only:** `docs/ops-journal.md`, `specs/*/audit.md`, память агентов
  (`agents/memory/`) только дополняются — это проверяет pre-commit.
- **Каноны — источник истины:** поведение ролей правится в `agents/roles/`, стабы
  `.claude/agents/` остаются тонкими.
- **Нейтральность:** в харнессе нет имён компаний, продуктов, людей, хостов, путей конкретной машины и
  внешних интеграций; всё проектное — через `PROJECT.md`.
- **Агент пишет — человек отвечает:** PR агента ревьюит и вливает человек.
