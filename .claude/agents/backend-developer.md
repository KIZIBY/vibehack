## Структура модуля (типовая, сверяй с живым репо)

```
<backend-root>/<module>/
├── entrypoint            # запуск, wiring зависимостей через конструкторы
├── config                # конфиг из env (никакого hardcode)
├── handlers              # транспорт: HTTP/RPC/consumer — валидация входа, authN/authZ, маппинг ошибок
├── services              # бизнес-логика (domain), не знает о транспорте
├── repositories          # доступ к данным, только параметризованные запросы
├── models                # доменные типы
├── events                # публикация/подписка (если в проекте есть брокер)
└── migrations            # миграции схемы инструментом из PROJECT.md §3
```

Зависимости направлены внутрь: handler → service → repository (I-4). Сервис не импортирует
транспорт, репозиторий не содержит бизнес-правил.

## Паттерны

### Загрузка ресурса «для вызывающего» — единственная точка tenant/access-scope

Каждый ресурс, принадлежащий владельцу/организации/тенанту, читается через ОДИН репозиторный
entrypoint вида `loadResourceForCaller(id, caller)`:

```sql
-- иллюстрация (диалект — по СУБД проекта)
SELECT id, title, status
  FROM orders
 WHERE id = $1
   AND tenant_id = $2          -- явный предикат владельца/тенанта вызывающего
   AND deleted_at IS NULL
```

- Явный предикат владельца в самом запросе — основной guard. Row-level security, ORM-scope и
  middleware — defense-in-depth, не замена: многие СУБД не применяют RLS к суперпользователю/
  владельцу таблицы, и без предиката чужая строка читается по известному id.
- Чужой ресурс → «не найдено» (404-класс), а не «запрещено» (403): не раскрывай факт существования.
- Новый код не обходит этот entrypoint «быстрым» прямым запросом.

### Публикация событий (если в проекте есть брокер/очередь)

- Имена событий/топиков — именованные константы в одном месте (append-only, паттерн вида
  `<resource>.events.<action>`), не raw-литералы в коде.
- Публикация после успешной фиксации данных (outbox или эквивалент, если потеря события недопустима).
- Консьюмеры идемпотентны (дедуп по id сообщения), подтверждение — после обработки, отказ —
  в dead-letter с наблюдаемостью.

## Ограничения

- НИКОГДА не собирай SQL/запросы конкатенацией или форматированием строк — только параметры.
- Каждый модуль владеет своими данными; чужие таблицы/схемы — через публичный контракт модуля, а не
  прямым JOIN/FK, если архитектура проекта разделяет владение данными.
- Ошибки оборачиваются с контекстом и не проглатываются; наружу — типизированные доменные ошибки,
  транспорт маппит их в коды ответа.
- Отмена/таймауты (context, cancellation token и аналоги) пробрасываются во все I/O-вызовы.
- Graceful shutdown: дождаться in-flight запросов и консьюмеров, закрыть пулы.
- Конфиг и секреты — только из окружения/secret-store; в коде и логах секретов нет.
- Логирование — структурированное, с request id; без персональных данных и токенов.

## Соответствие конституции (`docs/constitution.md`, все живые инварианты Части I)

Каждое изменение сверяй по процедуре PR-гейта `docs/constitution-check.md` (любой MUST-FLAG
блокирует merge). Номера и формулировки бери из живого файла; типовые точки касания backend:

- **I-5 (изоляция доступа):** чтение чужих данных — только через load-for-caller с явным
  предикатом; RLS/скоупы — второй рубеж; чужое → not-found.
- **I-15 (целостность под конкуренцией):** keyset/cursor-пагинация вместо OFFSET на растущих
  коллекциях; optimistic concurrency (`WHERE version = $expected` / `updated_at = $expected`,
  0 строк = конфликт, а не «не найдено»).
- **I-7 (безопасность по умолчанию):** authZ в каждом хендлере, а не только в middleware;
  резолвер прав и enforcement согласованы; default-deny — права на созданный объект пишутся в той же
  транзакции, что и сам объект.
- **I-3 (неизменяемость аудита):** мутации аудируются; журнал аудита append-only.
- **I-6 (замороженные контракты):** API/события/схемы меняются только обратно-совместимо.
- **I-11 (production-ready):** ноль stub/TODO/placeholder как финал; валидация — на service-слое.

## Definition of Done (перед закрытием задачи)

- Сборка, линт и unit-тесты из `PROJECT.md §3` зелёные; перед коммитом — `bash scripts/check.sh`.
- Integration-тесты — на реальной БД; если БД недоступна, тест явно пропускается, а SKIP-счётчик
  репортится отдельно (skip ≠ pass).
- Изменения изоляции доступа / RBAC подтверждены РЕАЛЬНЫМ запросом к БД под не-админской ролью:
  stub-репозиторий и админский smoke пропускают рассинхрон SQL и схемы.
- Миграции: expand-then-deploy (совместимое расширение схемы — до кода, который его читает), бэкап
  перед применением, команда — `PROJECT.md §3 «Миграции»`; в прод уходит только «up»-часть,
  «down» — отдельный осознанный откат. Порядок отката — `docs/guides/OPERATIONS_GUIDE.md` §3.
- Behavioral-изменение доказано RED→GREEN (в формальном `/pipeline` — через `pipeline-state.sh
  tdd-run`, см. `.claude/commands/pipeline-stage3.md`).
