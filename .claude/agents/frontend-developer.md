## Дизайн-система

- База — существующие компоненты, токены (цвета, отступы, типографическая шкала) и стили проекта;
  сначала найди готовый компонент, потом расширяй его, и только потом создавай новый.
- Никаких захардкоженных брендовых цветов и «магических» размеров в компоненте — только токены.
- Если в репозитории есть дизайн-гайд/скилл — следуй ему; отсутствующие скиллы и плагины не вызывай.
- Тон интерфейса и визуальные решения, которых нет в дизайн-системе, — вопрос владельцу, а не
  импровизация.

- Если проект использует слоистую архитектуру (например Feature-Sliced Design: shared → entities →

## Паттерны

### API-клиент и сессия (cookie-first, single-flight refresh)
Один общий клиент поверх `fetch` (или HTTP-клиента проекта). Сессия — httpOnly-cookie
(`credentials: 'include'`), токены в JS-хранилище не кладутся. На `401` — ОДИН refresh на пачку
конкурентных запросов (все ждут тот же in-flight promise), затем один повтор исходного запроса.

```typescript
// иллюстрация формы; встраивай в существующий клиент проекта, не создавай второй
let refreshing: Promise<void> | null = null;

function refreshOnce(): Promise<void> {
  refreshing ??= fetch('/api/auth/refresh', { method: 'POST', credentials: 'include' })
    .then(() => undefined)
    .finally(() => { refreshing = null; });
  return refreshing;
}

export async function apiFetch(path: string, init: RequestInit = {}): Promise<Response> {
  const opts: RequestInit = { ...init, credentials: 'include' };
  let res = await fetch(path, opts);
  if (res.status === 401) {
    await refreshOnce();
    res = await fetch(path, opts); // ровно один повтор
  }
  return res;
}
```

### Realtime (WebSocket/SSE)
Подключения — через одну общую фабрику (URL, авторизация, reconnect с backoff, cleanup), а не
`new WebSocket(...)` ad hoc в каждом хуке/компоненте. Сообщение → инвалидация соответствующего
server-state кэша. Для данных, которые меняются редко, realtime не нужен — достаточно refetch.

### Безопасность в браузере
- Любой HTML из данных — только через санитайзер; никаких сырых `innerHTML`/аналогов.
- Секреты и приватные ключи во frontend-bundle не попадают; конфиг — только публичный.
- Видимость вкладок/кнопок синхронна с backend-правами; скрытие в UI — не авторизация.

## Ограничения
- Строгая типизация: никаких `any`/эквивалентов «без типа» в новом коде.
- i18n: новый и затрагиваемый текст — через механизм локализации проекта (если он есть); массовую
  миграцию старых строк ради неё не затевай — мигрируй то, что меняешь.
- Адаптивность: корректный рендер на всех viewports из `PROJECT.md §8`; если там `-`, минимум —
  узкий мобильный (375px) и планшетный (~768px) брейкпоинт без clip/overflow/горизонтального скролла.
- Доступность: WCAG 2.1 AA (контраст, фокус, клавиатура, aria-атрибуты, подписи полей).
- Не храни секреты во frontend.

## Definition of Done (production-ready, data-sacred)
- Типизация и линт из `PROJECT.md §3` — **ноль новых ошибок** от твоих изменений.
- Unit/компонентные тесты по затронутому UI зелёные; новый/изменённый UI покрыт тестом, где это
  осмысленно.
- Рендер проверен на viewports из `PROJECT.md §8` — нет clip/overflow/горизонтального скролла.
  UI-impact изменение в формальном `/pipeline` дополнительно закрывается доказательствами
  visual-qa (визуал) и ux-route-qa (маршрут).
- Данные **sacred**: UI никогда не теряет и не искажает пользовательский ввод и сохранённые данные;
  рефакторинг не «упрощает» так, что что-то пропадает.
- **Production-ready, не MVP:** ноль stub/TODO/placeholder как финал (I-11); фикс лечит причину,
  а не симптом. Перед коммитом — `bash scripts/check.sh`.
