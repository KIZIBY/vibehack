## Изоляция данных по владельцу/тенанту

```sql
CREATE TABLE orders (
    id          UUID PRIMARY KEY,
    tenant_id   UUID NOT NULL,          -- владелец/тенант денормализован в КАЖДУЮ разделяемую таблицу
    title       TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'draft',
    created_by  UUID NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at  TIMESTAMPTZ
);
CREATE INDEX idx_orders_tenant ON orders(tenant_id);

-- defense-in-depth: row-level security (если СУБД поддерживает)
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
CREATE POLICY orders_tenant_isolation ON orders
    USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

Tenant-guard discipline: RLS — только второй рубеж. Многие СУБД не применяют RLS к
суперпользователю (а без `FORCE` — и к владельцу таблицы), ORM-скоупы обходятся сырыми запросами.
Поэтому единственный надёжный guard — явный предикат владельца в каждом чтении через единственный
entrypoint на ресурс (`loadOrderForCaller` и аналоги):
`WHERE id = $1 AND tenant_id = $2 AND deleted_at IS NULL` → «не найдено» (404-класс, без
existence-oracle). Без этого предиката чужая строка читается по известному id.

## Векторный поиск (только если проект хранит embeddings)

- Таблица чанков несёт `tenant_id` (и, если есть, владельца/ACL) — фильтр доступа применяется В
  запросе поиска, а не после top-K (иначе чужие чанки вытесняют свои и утекают через ранжирование).
- Индекс приближённого поиска (HNSW/IVF и т.п.) подбирается по объёму и профилю recall/latency;
  выбор фиксируется в plan с измерением.
- Пост-фильтр доступности документов после retrieval — дополнительный рубеж; пустой/нулевой
  `tenant_id` → отказ, а не «поиск по всем».
- Что вообще индексируется — whitelist источников; чувствительные источники исключены и закрыты
  регрессионным тестом.

## Миграции

- Каждая миграция — up + down либо явное «необратима + бэкап до».
- **Expand-then-deploy (expand/contract):** совместимое расширение (nullable-колонка, колонка с
  DEFAULT, новая таблица/индекс) применяется ДО деплоя кода, который его читает; удаление/сужение —
  отдельным шагом после того, как старый код выведен.
- В прод применяется только «up»-часть. Если инструмент хранит up и down в одном файле, а в проде
  его нет — никогда не пайпь файл целиком: down-секция (DROP/DELETE) уничтожит данные.
- Бэкап БД (dump/snapshot) — ДО любой миграции в проде (данные священны, I-2).
- Длинные операции (бэкфилл, построение индекса на большой таблице) — без долгих блокировок:
  батчами / конкурентным построением индекса, с оценкой времени.
- Применение — командой `PROJECT.md §3 «Миграции»`; откат — `docs/guides/OPERATIONS_GUIDE.md` §3.

## Паттерны запросов

### Только параметризованные запросы; keyset-пагинация вместо OFFSET (I-15)
OFFSET деградирует и пропускает/дублирует строки при вставках — используй курсор:
```sql
SELECT id, title FROM orders
 WHERE tenant_id = $1 AND status = $2 AND id > $3
 ORDER BY id
 LIMIT $4;
```

### Optimistic concurrency
UPDATE сверяет ожидаемую версию — расхождение = 0 строк = конфликт:
```sql
UPDATE orders
   SET title = $1, updated_at = now()
 WHERE id = $2 AND tenant_id = $3 AND updated_at = $4;
-- 0 affected rows → ошибка конкурентного изменения (а не «не найдено»)
```

### Пакетная запись
Массовые вставки — батчем/COPY драйвера в одной транзакции, а не N одиночных round-trip'ов.

## Ограничения
- НИКОГДА не собирай SQL конкатенацией строк.
- Первичные ключи — по конвенции проекта (UUID/identity), единообразно.
- Время — с таймзоной (`TIMESTAMPTZ` или аналог), не «наивное».
- Индексы на все внешние ключи и часто фильтруемые поля.
- Пагинация — keyset, не OFFSET, на растущих коллекциях.
- Optimistic concurrency — по версии/`updated_at`.
- Разделяемые таблицы: `tenant_id NOT NULL` + RLS/скоуп как второй рубеж; чтение — только через
  load-for-caller с явным предикатом.
- Если архитектура разделяет владение данными между модулями — без cross-module FK и JOIN в чужие
  схемы; связь через контракт модуля.

## Неизменяемость аудита (I-3)
Журнал аудита append-only на уровне самой БД: триггер, который отклоняет любой UPDATE/DELETE
(не только соглашение в коде). Легитимный бэкфилл — отдельной осознанной процедурой (feature-flag,
отдельное соединение, сам бэкфилл аудируется).

## Definition of Done (для любого DB-изменения)
- План выполнения (`EXPLAIN ANALYZE` или аналог) подтверждает индексный доступ на новых/изменённых
  горячих запросах, а не полный скан.
- Cross-tenant проверка: запрос под ЧУЖИМ `tenant_id` возвращает **0 строк**, а не чужую строку по id.
- Для изменений, затрагивающих RBAC/видимость, — РЕАЛЬНЫЙ запрос к БД под не-админской ролью:
  stub-репозиторий и админский smoke пропускают рассинхрон SQL и схемы.
- Миграция прогнана на копии/тестовой БД вперёд и назад (или зафиксирована необратимость + бэкап).
- Перед коммитом — `bash scripts/check.sh`.
