# /ship — задача → тест → код → ревью → публикация

Задача: **$ARGUMENTS**

Конвейер по умолчанию для фич и багфиксов (`AGENTS.md` → «Как вести работу»). Состояние живёт в
коммитах и телеметрии — без `state.md`, `audit.md`, квитанций, Root-печатей и owner-гейта до кода.
Формальный `/pipeline` (State V4) — только по явной просьбе владельца или для регулируемых работ.
Шаги опираются на исследования: TDD с тестами от отдельного агента, ревью другой моделью, ACE
(маленькие правки плейбука), MAST, METR (прогноз против факта).

## 0. Задача и прогноз — до любой работы

Hook телеметрии обычно уже открыл `T<n>` — дай прогноз и заголовок:
`bash scripts/telemetry.sh task estimate <id> <мин> --title "<3–6 слов>"`; иначе
`bash scripts/telemetry.sh task start auto --estimate <мин> --title "…"`.
Владелец назвал, сколько это заняло бы у человека без AI, — добавь `--human-estimate <мин>` (METR:
прогноз агента, оценка человека и факт — на одном графике).
Не понимаешь, что нужно, — один уточняющий вопрос владельцу до кода (не угадывай: MAST FM-2.2).

## 1. План — не больше 5 строк

Что меняем, какие файлы, критерий готовности, чем проверим. Нужен контекст по коду — субагент
`Explore` (возвращает вывод, не файлы). Риск по безопасности / данным / совместимости — одна строка
в описании коммита: что может сломаться и как откатить.

## 2. Тест первым — пишет отдельный агент

Субагент `test-runner` пишет падающий тест на критерий готовности и прогоняет его командой из
`PROJECT.md §3`. RED засчитывается, только если тест упал на ассерте, а не на окружении или компиляции.
Коммит `test(<scope>): RED <что проверяем>` — только файлы тестов, без кода продукта; запомни
`RED_SHA=$(git rev-parse HEAD)`.
Нечего тестировать автоматически (вёрстка, конфиг, документация) — пропусти шаг и напиши почему.

## 3. Код — до зелёного; тест не трогаем

Исполнитель меняет код продукта, пока тест не станет зелёным, а соседние тесты остаются зелёными.
Тест кажется неверным — не правь его сам: верни на шаг 2 с объяснением, что не так.
Перед ревью тест должен совпадать с RED: `bash scripts/ship-guard.sh "$RED_SHA"` → exit 0.
UI-изменение: открой страницу в браузере, сделай скриншот и проверь консоль на ошибки; полный прогон
`visual-qa` + `ux-route-qa` — перед релизом или демо, не на каждую задачу.

## 4. Ревью — другой моделью

Сначала — модель другого вендора: `bash scripts/review-cross.sh "$RED_SHA" <файл-с-выводом-тестов>`
(Codex, read-only; получает diff, тест из RED-коммита, вывод `ship-guard.sh` и твои доказательства;
exit 0 = APPROVE, 1 = BLOCK, вердикт сам пишется в телеметрию). Exit 2 (Codex недоступен, diff
слишком большой) — `code-reviewer` на модели, отличной от исполнителя (исполнитель на opus —
`model: sonnet`), на `git diff "$RED_SHA"` и новые файлы (`git status --short`) — код до шага 5 ещё
не закоммичен. У него нет Bash: вставь в задание diff и вывод `ship-guard.sh` и прогона тестов, а
новые файлы перечисли путями — он прочитает их инструментом Read. Вердикт **APPROVE** или **BLOCK** с находками P0–P2; любая P0/P1 —
BLOCK. BLOCK → правишь → повторное ревью. Два BLOCK подряд — стоп, к владельцу с находками: по кругу
не ходим.

## 5. Проверки и публикация

`bash scripts/check.sh` → коммит `feat|fix(<scope>): …` с трейлером `Co-Authored-By` →
`bash scripts/agent-publish-main.sh` (PR по умолчанию; соло-проект — `AGENT_PUBLISH_MODE=main`) →
`bash scripts/telemetry.sh task done <id>`.

## 6. Сбой — одна запись и одно правило

Сбой агента (исправление курса от владельца, ложное «готово», пропущенная проверка):
`bash scripts/telemetry.sh log mast code=FM-x.y note="…"` и предложи владельцу ОДНО правило, которое
закрыло бы такой сбой. После «ок» — датированная запись в `docs/pipeline-rules.md` (дата + источник)
и `bash scripts/telemetry.sh log rule ref=docs/pipeline-rules.md closes=FM-x.y`. Без «ок» правило —
только кандидат.

## Параллельно: 2–4 исполнителя

Независимые задачи (не трогают одни и те же файлы) — каждая в своём worktree и своей сессии:
`bash scripts/ship-worktree.sh new <slug>` → `cd` в напечатанный путь → там `/ship "…"`.
Не больше 4 одновременно (`ship-worktree.sh list` показывает `N/4`; пятый — отказ): по исследованию
CMU параллель даёт +15–25 п.п., а 8 агентов работают хуже 4. Сборка и тесты — по одному процессу
внутри worktree (устав 2.0.0, I-15), публикация в main — по одной на проект; телеметрия ведёт задачи каждого worktree отдельно. Задачи делят файлы — строго
последовательно в одном checkout.

## Чего здесь нет намеренно

`state.md`, `audit.md`, Design/Implementation/Evidence-Root, receipts, owner-гейта до кода, чек-листов
ролей и тяжёлых ролей (`developer`, `chaos-qa`). Всё это — в `/pipeline`, по явной просьбе.
