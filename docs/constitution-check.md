# Constitution Check — gate-процедура

**Статус:** canonical · операционный канон enforcement'а устава (см. [constitution.md](constitution.md), Часть III).
**Версия:** 1.0

**Что это.** Воспроизводимая процедура, которой stage-2 audit (`/pipeline-stage2`), ревьюер PR или
агент сверяют спеку / план / дифф с Частью I устава (инварианты I-1…I-17). Это и есть «авто-гейт»
enforcement'а: сверка переходит из «если ревьюер вспомнил» в обязательный шаг с правилом блокировки.

## Принцип DRY

Процедура **не дублирует** формулировки инвариантов. Единственный источник истины —
`docs/constitution.md`, Часть I. Здесь описано только КАК проверять и КАК блокировать. Путь устава —
`docs/constitution.md` (одна константа; при переносе файла обнови ссылку здесь и в
`.claude/commands/pipeline-stage2.md`).

## Вход

Любой из: `spec.md`, `plan.md`, дифф / PR или текстовое описание изменения.

## Процедура

1. Загрузи `docs/constitution.md` — Часть I (I-1…I-17, вместе с заполненными доменными слотами) и
   Часть III (precedence).
2. Для **каждого** инварианта I-1…I-17 оцени вход по его строке «_Как проверить_»:
   - **PASS** — соответствует, либо обоснованно неприменим;
   - **N/A** — инвариант не затрагивается изменением или помечен в уставе как `N/A` (укажи почему);
   - **FLAG** — изменение нарушает или вероятно нарушит инвариант (укажи, где и чем);
   - **NEEDS-INFO** — по входу инвариант оценить нельзя.
3. Не угадывай. Если данных не хватает — `NEEDS-INFO` + требование уточнить спеку, а не молчаливый
   PASS (I-13). Незаполненный слот `[ЗАПОЛНИ]` в затронутом инварианте — тоже `NEEDS-INFO`: правило
   уточняет владелец, а не аудитор.

## Выход (обязательный формат)

| Инвариант | Severity | Вердикт | Обоснование |
|---|---|---|---|
| I-1 «имя из Части I устава» | MUST/SHOULD | PASS/N/A/FLAG/NEEDS-INFO | … |
| … (все инварианты Части I, по порядку, с их именами из устава) … | | | |
| I-17 «имя из Части I устава» | … | … | … |

**Итог:** `MUST-FLAG: N · SHOULD-FLAG: N · NEEDS-INFO: N`.

> Severity берётся из заголовка самого инварианта в Части I (MUST/SHOULD); частично-N/A инвариант
> оценивается по его применимой части.

## Правило блокировки

- **Любой `MUST-FLAG` = блокер этапа.** Спека не проходит stage-2 (и PR не мержится), пока нарушение
  не устранено в спеке **ИЛИ** не проведена явная versioned-поправка устава (Часть III), легализующая
  исключение. Молчаливый обход запрещён (I-11 / I-13).
- **`NEEDS-INFO` на MUST-инвариант** = блокер до уточнения (непроверенное не пропускаем — I-13).
- **`SHOULD-FLAG`** — предупреждение: фиксируется в `plan.md` → «Known Risks», не блокирует.
- **Условный PASS** («PASS при условии решения плана D-*») — обязательство stage-4: stage-4 проверяет
  материализацию каждого такого условия в реализации; невыполнение возвращает FLAG.

## Self-тест (приёмка гейта)

Гейт обязан на эталонах давать ожидаемый результат, иначе он сломан. Эталоны ниже сформулированы на
нейтральном домене «заказы» и универсальных инвариантах; проект, у которого часть инвариантов
помечена `N/A`, формулирует пару spec-bad/spec-clean под свою заполненную Часть I.

- **`spec-bad`** (новая многопользовательская таблица заказов с прямым `SELECT` из handler'а без
  фильтра по владельцу/тенанту вызывающего, `OFFSET/LIMIT`-пагинация растущей таблицы, секрет
  литералом в compose-файле, **новый user-facing-эндпоинт без capture/correlate-пути ошибок** —
  клиентские 5xx/JS-исключения никуда не собираются и не коррелируются по `request_id`) → как минимум
  **FLAG I-5** (нет скоупинга по вызывающему → риск чужих данных + existence-oracle), **FLAG I-15**
  (offset вместо keyset), **FLAG I-7** (секрет в репозитории), **FLAG I-9** (нет хотя бы одного из
  CAPTURE/CORRELATE/RETAIN/TRIAGE для пользовательских ошибок фичи); `MUST-FLAG ≥ 4`.
- **`spec-clean`** (read-endpoint заказов: слои по I-4, загрузка только с фильтром по вызывающему +
  404 на чужой ресурс, keyset-пагинация, RBAC ↔ enforcement, аудит мутаций, optimistic concurrency,
  ошибки долетают до ingest с `request_id`) → все MUST = PASS/N/A; `MUST-FLAG: 0`.

## Локальный git-хук (pre-commit)

Рантайм-агностик guard — `.githooks/pre-commit` (трекаемый, срабатывает на `git commit` ЛЮБОГО
рантайма — Claude Code, Codex, голый git — в отличие от Claude-only `.claude/settings.json`),
активируется `bash scripts/install-git-hooks.sh` (`git config core.hooksPath .githooks`, раз на
клон/worktree; идемпотентно, отказ при конфликте). Это **machine-CHECK при коммите, дополняющий
конвенцию** (устав остаётся source-of-truth): (1) **append-only (I-2/I-3)** — правка/удаление/вставка
в середину существующих строк `docs/ops-journal.md` / `specs/*/audit.md` / changelog'ов спеки →
BLOCK; штатная дозапись (`scripts/ops-log.sh`, `scripts/pipeline-state.sh`) и создание нового журнала
проходят; (2) **секреты (I-7)** — паттерны `scripts/secret-patterns.sh` (облачные/провайдерские
ключи, private key, userinfo в URL) в добавленных строках → BLOCK (allowlist — файлы, документирующие
сами паттерны); (3) **лизы координации** — staged-путь под действующим чужим lease из
`coordination/leases/` → BLOCK (`scripts/coordination-lease.sh`); (4) TODO/FIXME без ссылки на тикет
или `TEMP:` → WARN (I-11). Сбой самого guard'а
fail-open (не роняет легитимный коммит). Полная сверка инвариантов Части I требует суждения
(Constitution Gate в stage-2 / ревью PR) — shell её не делает. `git commit --no-verify` блокирует
`.claude/hooks/bash-guard.sh`; в других рантаймах обход виден в истории постфактум.
