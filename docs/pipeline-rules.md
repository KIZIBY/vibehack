# pipeline-rules.md — подтверждённые владельцем правила процесса

> **Слоистая модель:** устав (`docs/constitution.md`) > доктрины (`AGENTS.md`, `docs/`, `docs/guides/`,
> каноны `agents/roles/`) > **эти правила** > сырые learnings (память агентов, отчёты стадий).
>
> Сюда попадают ТОЛЬКО правила, подтверждённые владельцем проекта. Каждая проектная запись: дата +
> источник (решение владельца, спека, инцидент) + само правило. Learning стадии или агента — это
> кандидат, а не правило: он становится правилом, только когда владелец его подтвердил.
> По I-17 устава это единственное легальное место для prose-правила без исполняемого пути; если
> правило удаётся превратить в тест/линт/guard — делай это, а запись оставь ссылкой на guard.
> Записи не переписываются задним числом: отменённое правило помечается новой записью.

## Базовые правила харнесса

Источник всех записей раздела — харнесс v1.0 (уроки эксплуатации, подтверждённые при поставке).
Проект может отменить или ужесточить любое из них записью в разделе «Проектные правила».

### Архитектура команд и скриптов

- **Недетерминированное — промпту, транзакционное — скрипту.** Классификация, диалог, оценка живут в
  промпт-команде; цепочки с внешними эффектами (create → verify → link) — одним bash-процессом с явными
  исходами на stdout. Смешение слоёв даёт полу-выполненные транзакции, которые промпт не умеет
  откатывать.
- **Порядок операций дешевле компенсаций.** Сначала локальное и обратимое (SPEC_DIR, `init`), потом
  внешнее и необратимое (тикет, публикация). Обратный порядок порождает компенсирующие операции
  (тикет-сирота при упавшем `init`), которые дороже и сами падают.
- **Классификатору — явный bias к дешёвой ошибке.** При неоднозначности выбирается ветка с дешёвой
  ценой ошибки (feature-путь легко переиграть в bugfix; обратная ошибка теряет контекст), и bias
  фиксируется ТЕКСТОМ в команде — молчаливый «здравый смысл» у каждой модели свой.
- **Перед постройкой enforcement для «пробела в конвенции» — сверь литерал prose, не парафраз.**
  (а) Прочитай точную формулировку конвенции до кода; (б) гейт в критическом пути проверяй против ВСЕХ
  санкционированных вызовов (grep потребителей, тест-фикстуры), не только «очевидного» флоу;
  (в) правки публикации и иного критического пути проходят adversarial stage-1 (hard-critic +
  независимая проверка). Аборт юнита на stage-1 — нормальная работа предохранителя.
- **Две независимые реализации одной семантики — обязательный кросс-тест.** Если предикат пришлось
  написать второй раз в другом слое, одна фикстура подаётся в ОБЕ реализации с ассертом согласия.
  Без общей функции только общий тест ловит дрейф (расширение I-4 на дублированную логику).

### Оркестрация, субагенты и непрерывность

- **Вложенные субагенты стадий — только синхронно.** Фоновый субагент, запущенный из фонового агента,
  отчитывается мимо родителя (родитель ждёт вечно, результат теряется). Фоновые агенты запускает только
  оркестратор; стадия внутри агента исполняет свои роли inline или синхронными субагентами.
- **Субагент не запускает верификационную сюиту в фоне с уступкой хода.** Фоновая задача не удерживает
  субагента: он завершает ход, не прочитав исход, и возвращает пустой отчёт. Внутриагентная
  верификация (сюита, convergence-check) — только синхронным foreground-вызовом; бриф субагента
  требует этого явно, оркестратор снимает результат сам (I-13).
- **`unit-done` — только после прочтения результата.** Запуск convergence-чека и `unit-done` не
  батчатся в один вызов; вердикт ставится после фактического чтения исхода. Непрочитанный результат ≠
  результат.
- **Инфра-смерть фонового stage-агента ≠ потеря прогресса.** Таймаут, обрыв соединения, отказ
  провайдера или исчерпанный лимит оставляют `state.md` с последним `unit-done` как точку
  возобновления. Продолжатель НЕ доверяет полуфабрикату умершего — zero-trust перечитывает код и дифф,
  доделывает или переписывает до полного convergence-check. State-машина + append-only audit делают
  стадию идемпотентно-возобновляемой (`docs/state-v4-recovery.md`).
- **Тяжёлая верификация при нестабильной сети — инлайн в main-loop.** Прогон полного тест-раннера,
  чтение кода и constitution-сверку stage-4 при нестабильной сети оркестратор выполняет напрямую, а не
  фоновым субагентом: main-loop стабильнее фоновых процессов.
- **Критерий worktree-per-unit — дизъюнктность файловых границ, а не логическая независимость.**
  Юниты делят файл → строго последовательно в основном checkout; границы дизъюнктны → параллельные
  правки легальны, worktree опционален. Один-за-раз (I-15) регулирует запуск build/test-процессов, а
  не редактирование дизъюнктных файлов.
- **Непрерывность цели.** Конец батча, контекста или хода модели не завершает цель. После каждого
  батча оркестратор перечитывает последнюю явную цель, заново оценивает полный scope, проверяет каждый
  критерий завершения и продолжает следующий bounded batch без generic «что дальше?». Ход
  заканчивается только одним из исходов: доказанный `DONE` (с полной перепроверкой), typed
  `WAIT_OWNER` (нужно решение или authority владельца — сказать явно) или реальный `BLOCKED`. Каждый
  статус и финал содержит 1–3 ранжированные advisory-рекомендации, не меняющие scope и authority.
  Обещание «дальше сделаю X» в тексте сводки продолжением не является (I-14).
- **Переговоры параллельных сессий — до захвата ресурса.** Перед крупной работой (lease на
  spec-dir/подсистему, публикация в main, длинная правка общего ресурса) сессия сначала уведомляет
  другие активные сессии проекта о намерении (какой ресурс, какая спека) и только потом делает
  `bash scripts/coordination-lease.sh take`. Факт уведомления фиксируется событием `coord:*` в
  `docs/ops-journal.md` через `bash scripts/ops-log.sh` — это рантайм-агностичный канал; средства
  конкретного рантайма — лишь ускоритель. Причина: git не даёт распределённого лока, lease виден другим
  только после push+fetch.

### Гейты и уверенность

- **Условный PASS constitution-gate = обязательство stage-4.** Если stage-2 ставит инварианту PASS
  «при условии решения плана D-*» (закрыт дизайном, а не готовым кодом), stage-4 ОБЯЗАН проверить
  материализацию каждого такого обязательства; невыполнение реанимирует FLAG. Условный PASS —
  отложенная проверка, не индульгенция.
- **Confidence-контракт стадий — fail-safe направленность.** Стадия декларирует уверенность:
  `bash scripts/pipeline-state.sh stage-done <SPEC_DIR> <stage> [green|yellow|red] "причина"`.
  Non-green механически блокирует следующий `check` до `ack` владельца; **green никогда не
  разблокирует** (самодекларация модели не открывает гейт); молчание ≠ green. Механический пол против
  green-театра: `stage-done … green` отклоняется при `MUST-FLAG>0`, `quality-verdict: FAIL` или
  незакрытых юнитах. `ack` — атрибуция решения человека; self-ack агентом запрещён. Публикация при
  `PIPELINE_SPEC_DIR` гейтится `check publish`.
- **UI/UX-impact закрывается двумя независимыми оптиками (fail-closed).** Browser-rendered/UI-impact
  задача не закрывается без exact served identity, двух разных session/actor ID и двух разных
  artifact ID: visual-qa (screenshot + DOM/console/network) и ux-route-qa (действия/переходы/scroll/
  время, no-regression). Нет headed-браузера или одной из оптик → `CAPABILITY-BLOCKED` в тикете/ревью,
  закрытие запрещено; static/headless до PASS не повышается.

### Метрики и журналы

- **Честность usage-метрик.** События `usage:*` в `audit.md` пишутся ТОЛЬКО из реальных данных среды
  (отчёт инструмента субагента, hook, CLI-отчёт) с обязательным `source=`; оценка модели «по ощущениям»
  запрещена; отсутствие данных рендерится честным «нет данных», никогда — выдуманным числом.
  Исполняемая пара: `scripts/dora-metrics.sh` не засчитывает событие без `tokens=<int>` и непустого
  `source=`. Detail usage-событий попадает в git — никаких секретов и путей машины.
- **Одно usage-событие на агента-исполнителя.** `usage:agent:<имя>` пишет только фактический расход
  этого субагента; оркестратор не пишет зонтичных/суммарных usage-событий поверх отчётов субагентов —
  иначе двойной счёт в агрегатах.
- **Flight Deck — generated.** `docs/pipeline-dashboard.html` в git не коммитится и руками не
  правится; перегенерация — `bash scripts/pipeline-dashboard.sh` на границе каждой стадии и перед
  отчётом владельцу.
- **Execution-grounded eval.** `bash scripts/agent-eval.sh` меряет `% Resolved` курируемых задач
  `tests/agent-evals/NNN-slug/` контрактом FAIL→PASS ∧ PASS→PASS по exit-коду (не по прозе и не
  LLM-судьёй) в изолированном worktree/tmpdir. Правку канонов/скриптов, влияющую на способность
  решать задачи, прогоняй до и после — Δ resolution делает улучшение измеримым, а не «кажется лучше».
  Единственный сток — `tests/agent-evals/last-run.json` (generated); прямой `>>` в `*.md` запрещён (I-3).
  `verify.sh`/`snapshot.sh` задач — доверенный код с правами оператора: ревьюить как скрипты.

### Тесты и фикстуры

- **Тест-вызовы журнальных скриптов — только из фикстурного cwd.** `scripts/ops-log.sh` и
  `scripts/pipeline-state.sh event` в тестах вызываются с `cd` во временный фикстурный репозиторий,
  НИКОГДА из корня живого проекта: скрипты пишут в журнал по `git rev-parse --show-toplevel`, и
  фикстурная строка попадает в живой `docs/ops-journal.md`.
- **Постоянная негатив-ловушка мутирует только копию.** Тест, намеренно ломающий скрипт/конфиг для
  проверки защиты, работает на временной копии; прод-файл не мутируется даже транзиентно.
- **Git-фикстуры — от «сегодня», не до эпохи.** `git log --since="36500 days ago"` (до 1970) тихо
  отдаёт пустой лог: git-зависимые фикстуры строить на датах от текущего момента; широкое окно
  `--days` безопасно только для фильтра по времени в коде, не для самого `git log`.
- **Анти-дрейф-тест проверяет ключи фактического вывода, не пересчёт.** Тест наличия производных полей
  утверждает `exists $json->{field}` на РЕАЛЬНОМ выводе тракта (на обоих концах при pass-through), а не
  пересчитывает значение той же функцией — пересчёт зелёный и на тракте без эмиссии. Обязательный
  спутник — негатив-ловушка (порча копии тракта → проверка падает).
- **Grep-ассерт матчит форму записи в исходнике.** Атрибут, который ставится из JS, грепается
  setAttribute-литералом (`"attr", "value"`), статический — HTML-литералом (`attr="value"`). Форма
  выбирается ДО написания ассерта, чтением кода.
- **Числовые предпосылки спеки переизмеряются вживую на stage-1**, если источник данных доступен
  (live-эндпоинт, реальный каталог, журнал): числа из чужих отчётов и фраз — вход для проверки, не
  факт.

### Ловушки shell и perl

- **zsh `$a:start`.** Trace-события `agent:<имя>:start|done` в zsh писать литералом или `${a}:start`,
  НЕ `$a:start`: модификатор `:s` съедает суффикс и портит имя агента в таймлайне.
- **Perl: capture-группу — в переменную сразу.** `$1` живёт до следующего успешного match: регекс
  между захватом и использованием затирает его. Правило: `my $x = $1;` немедленно после match. Smoke
  нетривиальных perl-ветвей обязателен — сюита ловит не всё.
