# Устав проекта — операционная конституция

**Статус:** canonical · верховный закон репозитория. Единый свод неизменных принципов, из которых
выводятся решения по продукту и процессу.
**Версия:** 2.0.0 · **Принят:** 2026-10-25 · **Owner:** владелец проекта (`PROJECT.md §1`)
**Применяется к:** всем агентам, оркестратору `/pipeline`, speckit-потоку и людям-контрибьюторам.
**Модель документа:** apex + ссылки — устав владеет принципами и индексом канонов (Часть II), детали
живут в канонах.

> **Как заполнить.** Устав поставляется вместе с харнессом как шаблон: 17 универсальных инвариантов
> выведены из боевых уроков и применимы к любому проекту, доменные места помечены
> `[ЗАПОЛНИ: …]`. Заполни слоты под свой продукт (`PROJECT.md` подскажет стек и окружения).
> Неприменимый инвариант не удаляется молча — пометь его `N/A` с причиной (например, I-5 для
> однопользовательского инструмента). Ослабление универсального инварианта после принятия — только
> поправкой владельца (Часть III). Сверка спек/планов/диффов — `docs/constitution-check.md` (DRY:
> читает Часть I этого файла).

---

## Преамбула — две супер-ценности

> **1. Данные священны.** Пользовательские данные, журналы и память агентов не теряются и не
> искажаются молча; история изменений сохраняется.
>
> **2. Только production-ready.** То, что попадает в main, протестировано и связно:
> `bash scripts/check.sh` зелёный перед каждым коммитом; конвенция без исполняемого пути — не конвенция.

Нарушение любого MUST-инварианта Части I — блокер (коммита, публикации, закрытия юнита или тикета),
пока нарушение не устранено или не проведена явная поправка устава (Часть III).

## Как пользоваться

- **Перед архитектурным или процессным решением** пройди Часть I; предложение, нарушающее инвариант,
  отвергается или требует явной поправки, а не молчаливого обхода.
- **Проверка риска:** обычная работа сверяет решение с Частью I в спеке/PR/review. Если владелец или
  проект выбрал формальный `/pipeline`, stage-2 дополнительно проходит
  [docs/constitution-check.md](constitution-check.md).
- **Агенты** сверяются с уставом перед действием; `AGENTS.md`, доктрины и `docs/pipeline-rules.md` —
  подчинённые конкретизации (precedence — Часть III).

## Часть I — 17 инвариантов

### Данные

#### I-1 — Data Sovereignty & Deployment Model (суверенитет данных)
**MUST.** Данные продукта (проекты, материалы участников, баллы, журнал) живут на сервере
платформы владельца: БД и том материалов. За периметр уходят только: (а) запросы к модели OpenAI
через Hermes Agent — материалы участников туда отправлять **разрешено** (решение владельца
2026-10-25); (б) запросы веб-поиска и обращения к публичным хостам команд — без содержимого
закрытых материалов; (в) клонирование репозиториев по ссылкам, которые дал организатор. Любой
другой внешний LLM/SaaS, аналитика и трекеры с данными продукта — запрещены. Материалы участников
хранятся **7 дней** (решение владельца 2026-10-25; срок настраивается), затем содержимое файлов
удаляется, а записи, баллы и журнал остаются (см. I-2). Секреты участников, найденные в материалах,
маскируются до записи в журнал и отчёты.
Независимо от модели: в репозитории, журналах и тикетах нет путей конкретной машины, персональных
данных владельца и адресов приватной инфраструктуры.
- _Как проверить:_ спека/дифф не добавляет egress данных за заявленный периметр; контент не несёт
  литералов среды.

#### I-2 — Data is Sacred (данные священны)
**MUST.** Только soft-delete (`deleted_at` или аналог), миграции обратимы, append-only журналы
(`docs/ops-journal.md`, `specs/*/audit.md`, память агентов) не чистятся и не переписываются,
`.env`/конфиги окружений не перезаписываются деплоем. Пользовательские данные не теряются молча.
- _Как проверить:_ в диффе нет DELETE без soft-delete-обоснования, нет DROP/rewrite-миграций без
  бэкапа; pre-commit не сообщает о правке прошлых строк журнала.

#### I-3 — Audit Immutability (неизменяемость аудита)
**MUST.** Журнал бизнес-событий append-only: таблицы `journal_event` и `score_override` с
триггерами БД, запрещающими UPDATE и DELETE, и файл `runs/<run_id>/journal.jsonl`, в который агентский
слой только дописывает. Мутации значимых сущностей (рубрика, баллы, ручные правки, перезапуски,
удаление по сроку хранения) аудируются.
- _Как проверить:_ новая мутация пишет audit-событие; защита журнала на месте.

### Архитектура

#### I-4 — Clean Architecture (чистая архитектура)
**MUST.** Backend: router → service → repository; зависимости направлены внутрь и подставляются
через интерфейсы (шлюз агентов, хранилище файлов, часы). Frontend ходит только в REST API backend.
Агентский слой (`hermes/`) не пишет в БД: результат ролей попадает в платформу через инструменты
плагина (валидация по схеме из `specs/001-ai-judge-platform/contracts/`) и файлы на общем томе, а
принимает и сохраняет их backend. Модуль intake — отдельный процесс с контрактом `inventory.json`.
Итог баллов считает единственная функция `compute_score` (`hermes/plugins/ai-judge/tools.py`);
backend подключает её, а не копирует.
Один источник истины на каждое знание: дублированная логика либо выносится, либо покрывается общим
кросс-тестом.
- _Как проверить:_ дифф не протаскивает зависимость через слой / в чужую схему и не заводит второй
  источник истины.

#### I-5 — Tenant/Access Isolation (изоляция доступа) — если продукт многопользовательский/многотенантный
**MUST.** Первая версия — один общий демо-аккаунт (`PROJECT.md §6`, решение владельца 2026-10-25),
поэтому изоляция между пользователями **N/A**: все проекты видит единственная роль. Обязательное
остаётся: fail-closed — любой маршрут, API и файл без сессии отвечает отказом; материалы раздаются
только через backend; агент видит каталог одной работы, а не весь проект. Когда появятся
пользователи или роли, пометка N/A снимается и действует правило: ресурс загружается только с
фильтром по владельцу вызывающего, чужой ресурс = 404.
- _Как проверить:_ чтение/мутация/экспорт чужого ресурса по прямому ID — denied; малформ-пейлоад не
  становится оракулом.

#### I-6 — Frozen Contracts (замороженные контракты)
**MUST.** Обратная совместимость: замороженные поверхности — файлы в
`specs/001-ai-judge-platform/contracts/` (REST API `/api/v1`, `agent-report`, `inventory`,
`journal-event`, события SSE) и ответ `compute_score`. Поля не удаляются и не переименовываются;
расширение — новыми необязательными полями или новой версией схемы (`schema_version`).
- _Как проверить:_ дифф не меняет замороженную поверхность без versioned-решения владельца.

### Безопасность

#### I-7 — Security by Default (безопасность по умолчанию)
**MUST.** Авторизация на каждом endpoint; RBAC и enforcement синхронны (право видно в UI ⇔ проверка
на бэкенде); только параметризованные запросы к БД; секреты — env/secret-store, НИКОГДА в репозитории,
логах, тикетах, скриншотах и памяти. Вход и роли — по доктрине `docs/guides/AUTH_GUIDE.md` (§3–§4);
модель входа, провайдер и группа администраторов — `PROJECT.md §6`.
- _Как проверить:_ constitution-check по диффу; спека содержит `## Authentication & Access`;
  pre-commit не находит секрет-паттернов.

### Эксплуатация

#### I-8 — Graceful Degradation (деградация без падения)
**MUST.** Отказ опциональной подсистемы (агенты на OpenAI/Hermes, веб-поиск, браузер дизайнера,
расшифровка видео, git-хостинги команд) не роняет ядро: проекты, загрузка, рубрика, таблица оценок
и журнал работают, а затронутые критерии получают статус «нет данных» с причиной.
- _Как проверить:_ выключенная подсистема → ядро работает, ошибка видима оператору (I-9).

#### I-9 — Observability (наблюдаемость)
**MUST.** Structured-логи, health-check и метрики на каждый сервис; user-facing ошибки
перехватываются и коррелируются request/trace-id, retention ≥ 30 дней; всплеск ошибок
алёртится и заводится тикетом без ожидания жалобы пользователя.
- _Как проверить:_ у новой фичи ошибочные пути долетают до ingest с request_id
  (`docs/guides/NFR_GUIDE.md` §2).

#### I-10 — Deploy Safety (безопасный деплой)
**MUST.** Деплой только командой из `PROJECT.md §3` (`bash scripts/deploy.sh`; пока скрипта нет —
задача T095 плана, агентский слой выкатывается `bash hermes/deploy.sh`); миграции отдельно
от кода (expand-then-deploy), бэкап до; после деплоя — verify (health + smoke), откат описан
(`docs/guides/OPERATIONS_GUIDE.md` §3). Публикация в main — только `scripts/agent-publish-main.sh`
или PR.
- _Как проверить:_ дифф не вводит ручной деплой-шаг; у миграции есть Down/план отката.

### Процесс

#### I-11 — Production-Ready by Default (без MVP-заглушек)
**MUST.** Ноль stub/TODO/placeholder как финальное состояние; фича = код + тесты + документация;
workaround только помеченный `// TEMP: <причина>, см. <тикет или пункт docs/backlog.md>`.
`bash scripts/check.sh` зелёный перед каждым коммитом.
- _Как проверить:_ grep диффа на stub/TODO без ссылки; DoD stage-4 (или PR-чек-лист) зелёный.

#### I-12 — Root-Cause Discipline (дисциплина первопричины)
**MUST.** Любой баг — через systematic debugging до доказанной первопричины; scope-the-class (все
оси повторения) + guard от регрессии. Канон: `docs/bug-handling-process.md`.
- _Как проверить:_ фикс несёт доказательство root cause и регрессионный тест/guard.

#### I-13 — Zero-Trust Verification (никому не верь на слово)
**MUST.** Claim (агента, CI, репортёра, своей памяти) принимается только со свежим собственным
evidence, желательно на другой оси. «FIXED» без перепроверки не существует.
- _Как проверить:_ у закрытия есть воспроизводимый вывод (тест, repro, браузерный раунд-трип),
  полученный проверяющим, а не пересказ.

#### I-14 — Code Speaks, Not Comments (код, а не комментарии)
**MUST.** Самодокументируемый код; комментарий-обещание («сервис X гарантирует Y» без реальной
проверки) запрещён; комментарий допустим только для ограничения, которое кодом не выразить.
Обещание «дальше сделаю X» в отчёте агента продолжением не является.
- _Как проверить:_ в диффе нет комментариев, подменяющих проверку или вызов.

### Целостность

#### I-15 — Data Integrity Under Concurrency (целостность под конкуренцией)
**MUST.** Optimistic concurrency на конкурентных мутациях (колонка `version`, запись
`UPDATE … WHERE id = $id AND version = $expected`, при несовпадении — 409; в одной работе не больше
одного активного прогона роли — уникальный индекс), bounded-выборки (keyset вместо OFFSET на растущих таблицах).
Мутирующие процессы разработки (build, тесты) — строго один за раз в пределах git worktree;
параллельных worktree-исполнителей — не больше 4 (`scripts/ship-worktree.sh`); публикация в общую
ветку — строго одна за раз на весь проект.
- _Как проверить:_ конкурентная мутация не теряет чужую запись; списки на растущих таблицах
  пагинируются keyset.

#### I-16 — Requirements Traceability (прослеживаемость требований)
**MUST.** Каждое требование спеки имеет след в плане и проверку в приёмке (`scripts/plan-lint.sh` +
requirements-matrix stage-4); NFR квантифицированы (`docs/guides/NFR_GUIDE.md`).
- _Как проверить:_ у каждого FR/NFR есть строка в плане и способ проверки; `plan-lint` зелёный.

### Enforcement конвенций

#### I-17 — Convention → Executable Path (конвенция → исполняемый путь)
**MUST.** Конвенция проекта существует, только если у неё есть исполняемый путь: тест, линт, guard в
скрипте или git-хуке, гейт state-машины либо шаг `scripts/check.sh`. Generated-артефакты
(`docs/pipeline-dashboard.html` и т.п.) руками не правятся — только генератором; если артефакт
трекается, регенерация идёт в том же коммите, что и правка источника, а drift-проверка валит
`check.sh`. Prose-правило без enforcement допустимо только как датированная запись в
`docs/pipeline-rules.md`, подтверждённая владельцем.
- _Зачем:_ правило, которое держится на внимании агента, не переживает свежий контекст; дрейф
  generated-файла создаёт второй источник истины (I-4).
- _Как проверить:_ у новой конвенции в диффе виден её guard (строка теста/линта/хука/скрипта) либо
  датированная запись в `docs/pipeline-rules.md`.

## Часть III — precedence, поправки, enforcement

### Precedence

```
Устав (этот файл)
  > доменные каноны (AGENTS.md, доктрины docs/ и docs/guides/, каноны agents/roles/)
  > docs/pipeline-rules.md (подтверждённые владельцем правила процесса)
  > адаптеры рантайма (CLAUDE.md, .claude/*)
  > память агентов и сырые learnings
```

### Поправки (amendment)

Инвариант изменяется только явной поправкой: PR + bump версии (**MAJOR** — удаление/ослабление
инварианта, **MINOR** — добавление/усиление, **PATCH** — редактура без смены сути) + запись в журнал
ниже. Заполнение слотов `[ЗАПОЛНИ]` при установке поправкой не считается. **Молчаливый обход
инварианта — нарушение** (I-13).

### Enforcement

- **Тест-гейт:** `bash scripts/check.sh` перед каждым коммитом (I-11), включая guards конвенций (I-17).
- **Commit-гейт:** `.githooks/pre-commit` (активация — `bash scripts/install-git-hooks.sh`):
  append-only журналы (I-2/I-3), секреты (I-7), пути под чужим lease координации,
  TODO/FIXME без ссылки — предупреждение (I-11).
- **Publish-гейт:** `bash scripts/agent-publish-main.sh` — проверки до push, verify-after-push,
  DORA-события (I-10, I-13).
- **Дифф-гейт:** ревьюер PR проверяет инварианты соразмерно риску.
- **Formal spec-гейт:** при выбранном формальном `/pipeline` Constitution Gate stage-2 по
  [docs/constitution-check.md](constitution-check.md) блокирует stage-3 при `MUST-FLAG`; stage-4
  проверяет материализацию условных PASS.
