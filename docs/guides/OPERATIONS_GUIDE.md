# OPERATIONS_GUIDE.md — эксплуатация: инциденты, runbook'и, откат, DORA

Status: ДЕЙСТВУЮЩИЙ (v1.0). Закрывает operation-фазу жизненного цикла: наблюдаемость ловит ошибку
(инвариант I-9 устава `docs/constitution.md`), этот док определяет, что происходит дальше.
On-call = владелец; агенты диагностируют, чинят по процессу и эскалируют — не «дежурят» молча.
Окружения и health-check — `PROJECT.md §4`; команды деплоя и отката — `PROJECT.md §3`.

---

## 1. Incident response — единый цикл

1. **Детект.** Источник: alert наблюдаемости / всплеск error-группы / жалоба. Всё user-facing
   обязано долетать до ingest с request_id (устав I-9 + `NFR_GUIDE.md` §2 Observability) —
   «пользователь заметил раньше системы» само по себе инцидент процесса, фиксируется как learning.
   Открытие инцидента — `bash scripts/ops-log.sh incident:open <slug>`.
2. **Триаж.** Severity по шкале bug-handling: **P0** — прод лежит/данные под угрозой (немедленно,
   будим владельца), **P1** — ключевой флоу сломан (в работу сразу), **P2/P3** — в очередь по
   приоритету. Тикет (или пункт `docs/backlog.md` при `ISSUE_BACKEND=none`) заводится ДО фикса
   (`docs/bug-handling-process.md` §1, dedup обязателен).
3. **Mitigate ≠ fix.** Сначала остановить ущерб: откат деплоя (§3), выключение опциональной
   подсистемы (graceful degradation, I-8), rate-limit. Mitigation помечается
   `// TEMP: <причина>, см. <тикет или пункт backlog>` — заплатка без задачи запрещена (I-11).
4. **Root cause.** После стабилизации — ОБЯЗАТЕЛЬНЫЙ systematic debugging до доказанной
   первопричины + scope-the-class (`bug-handling-process.md` §2/§4). Инцидент без root cause
   не закрывается. Закрытие — `bash scripts/ops-log.sh incident:resolved <slug>` (пара для MTTR).
5. **Post-mortem (для P0/P1).** Короткий разбор в `docs/incidents/<YYYY-MM-DD>-<slug>.md` (каталог
   создаётся первым post-mortem'ом): таймлайн (детект → mitigate → fix), первопричина, «почему не
   поймали раньше» (дыра наблюдаемости? → отдельная задача), предложенные правила → после
   подтверждения владельцем в `docs/pipeline-rules.md` или поправкой устава. Без поиска виноватых —
   ищем дыру в процессе.

## 2. Runbook-конвенция

- Путь: `docs/runbooks/<сервис|подсистема>.md` (каталог создаётся вместе с первым сервисом).
  Runbook обязателен для каждого сервиса/критичной подсистемы и создаётся ВМЕСТЕ с ним (tech-writer
  проверяет на stage-4 или в PR), не «потом».
- Минимум разделов: **Как понять, что сломалось** (health, дашборд, типовые сигнатуры ошибок) ·
  **Как перезапустить безопасно** (команды, порядок, что НЕ трогать) · **Известные грабли**
  (инциденты с датами и ссылками на задачи) · **Зависимости** (что тянет за собой).
- Runbook — живой: после каждого инцидента дополняется (та же дисциплина, что память агентов:
  append, не переписывание истории).

## 3. Откат (rollback)

- Деплой проекта обязан уметь откат на предыдущую версию кода; команда отката — `PROJECT.md §3` и
  runbook.
- Миграции: expand-then-deploy (сначала совместимая миграция, потом код); у каждой миграции есть
  Down-план ИЛИ явное «необратима + бэкап до». Откат кода без отката данных — штатный путь; откат
  данных — только владелец.
- После любого отката — verify как после деплоя (health + smoke) + задача на первопричину: откат —
  это mitigation, а не решение.

## 4. Роли

| Кто | В инциденте |
|---|---|
| Владелец | on-call, решения P0 (откат данных, downtime, коммуникация) |
| developer | диагностика + фикс по bug-handling; обновление runbook'а после фикса |
| workflow-qa · chaos-qa | функциональная проверка фикса и соседних сценариев |
| visual-qa · ux-route-qa | для UI-impact — визуальное и маршрутное доказательство в разных сессиях на exact served identity (zero-trust: «FIXED» без evidence не существует) |
| regression-qa | e2e-регрессия после фикса или отката, триаж падений |
| tech-writer | post-mortem, актуальность runbook'ов |

Эскалация всегда явная: задача + `NEEDS_ORACLE`/обращение к владельцу — «понадеялся, что заметит» =
потерянный инцидент.

## 5. Метрики: DORA и контракт автономии

**Рабочая панель** — Flight Deck: `bash scripts/pipeline-dashboard.sh` → `docs/pipeline-dashboard.html`
(DORA-блок сверху + trace прогонов; generated, в git не коммитится). Терминальный срез:
`bash scripts/dora-metrics.sh [--days N]`. Источники — только локальные файлы репозитория:
git-история, `specs/*/audit.md`, `docs/ops-journal.md`.

| Метрика | Как считается | Кто обязан кормить |
|---|---|---|
| Deployment Frequency | `deploy:done` в `docs/ops-journal.md` за окно; если в журнале нет ни одного `deploy:*` (у проекта нет деплой-шага) — `publish:done` | деплой-скрипт проекта в конце зовёт `bash scripts/ops-log.sh deploy:done "sha=<sha>"` (fail-ветка — `deploy:failed`); `scripts/agent-publish-main.sh` пишет `publish:*` сам и деплоем не считается |
| Lead Time | медиана `init` → `quality-verdict PASS` по `audit.md` прогонов | state-машина пишет сама |
| Change Failure Rate | `deploy:failed` / (`deploy:done` + `deploy:failed`) (без деплоев — то же по `publish:*`); инциденты окна показываются рядом, но в формулу не входят | деплой-скрипт (или publish при fallback); инциденты — триаж (§1) |
| MTTR | медиана `incident:open <slug>` → `incident:resolved <slug>` | триаж (§1): open при детекте, resolved после root-cause фикса |
| **Автономия** | агентные коммиты (трейлер `Co-Authored-By`) / все коммиты за окно | конвенция коммитов (`AGENTS.md` → «Публикация») — метрика собирается сама |

**Контракт автономии:** цель — **≥40% изменений в автономном цикле** (порог — env
`AUTONOMY_TARGET`, по умолчанию 40). Панель красит метрику красным ниже цели. Метрика честная и
грубая (по маркеру коммитов); дополнительный срез — гейты владельца (approved/revise) из `audit.md`:
много revise = автономия «формальная». Ниже цели → причина разбирается как learning (что блокирует
агентов), а НЕ накруткой коммитов (zero-trust применим и к своим метрикам).
