# AUTH_GUIDE.md — аутентификация и доступ продукта

Status: ДЕЙСТВУЮЩИЙ (v1.0). Параметры проекта — `PROJECT.md §6` (модель входа, провайдер/issuer,
группа или роль администраторов); тестовые пользователи QA — `PROJECT.md §5`; `LIVE_URL` —
`PROJECT.md §4`. Где работает: секция `## Authentication & Access` в спеке (проверка —
`scripts/spec-lint.sh`), аудит `/pipeline-stage2`, code-review auth-кода.

Модель входа `none` (у продукта нет пользовательского входа) — доктрина спит, но секция
`## Authentication & Access` в спеках всё равно обязательна (явное N/A, см. §3).

---

## 1. Правило по умолчанию

**Модель входа продукта одна и фиксируется в `PROJECT.md §6`; каждая фича следует ей, а не
изобретает свою.** Для продукта с организационными пользователями предпочтителен внешний
identity provider (OIDC или SAML; например корпоративный SSO или облачный IdP)
вместо самодельного логина/пароля: роли управляются централизованно (группы каталога → роли
продукта), 2FA и политика паролей наследуются от IdP. Собственная аутентификация (логин+пароль),
демо-режим или публичный продукт без входа — явное решение владельца, зафиксированное в
`PROJECT.md §6` и в спеке (`## Authentication & Access` + `## Assumptions`); собственный вход
обязан выполнять инварианты §4.

Fallback-правило: локальная аутентификация при недоступности IdP — только для УЖЕ провиженных
пользователей, НЕ безусловный auto-provision любого входящего.

## 2. При старте (установка харнесса в проект)

1. **Паспорт:** заполни `PROJECT.md §6` (модель входа, issuer, группа администраторов) и
   `PROJECT.md §5` (тестовые пользователи; пароли — только имена env-переменных).
2. **Текущий механизм:** первая спека, затрагивающая вход, фиксирует, как устроена аутентификация
   сейчас: провайдер, где живёт auth-код, откуда берутся роли, как логинятся тестовые пользователи.
3. **Регистрация приложения в IdP** (если интеграции ещё нет) — через администратора IdP или службу
   безопасности. Заявка содержит:

| Параметр | Значение |
|---|---|
| Название приложения | из `PROJECT.md §1` |
| Redirect URI | `<LIVE_URL>/auth/callback` (+ dev-URI отдельной строкой) |
| Logout URI | `<LIVE_URL>/` |
| Scope | `openid profile email` (+ claim групп, если IdP отдаёт роли через него) |
| Тип клиента | по решению безопасности: confidential (server-side, client_secret) ИЛИ public + PKCE S256 |

   Получаешь: client ID, client secret (только для confidential), issuer, документацию API. Имена
   групп каталога для ролей согласуются там же (пример маппинга: группа администраторов из
   `PROJECT.md §6` → `admin`, группа «все пользователи» → `user`). Значения секретов в репозиторий,
   тикеты и чат не попадают — только в secret-store/env.

## 3. При работе с требованиями (BLOCKING для spec-этапов)

Каждая спека фичи, затрагивающей **вход, пользователей, роли или доступ**, обязана содержать
секцию `## Authentication & Access` (шаблоны: `/speckit.specify`, `/pipeline-stage1`; проверка:
`scripts/spec-lint.sh`, security-ревьюер и Constitution Gate в `/pipeline-stage2`). Минимум секции:

- **Способ входа:** модель из `PROJECT.md §6` (по умолчанию) / исключение с обоснованием и решением
  владельца.
- **Источник ролей:** группы IdP/каталога или собственная модель ролей → маппинг на роли продукта
  (таблица; группа администраторов из `PROJECT.md §6` → admin).
- **Сессии:** logout (локальный + IdP-logout, если есть IdP), истечение/refresh, ревокация при
  деактивации пользователя.
- **Тест-доступ для QA:** тестовые пользователи `PROJECT.md §5` и/или тест-байпас — как QA-агенты
  входят (§5).
- **NFR-ссылка:** инварианты §4 применимы — отметить затронутые.

Фича не затрагивает вход/доступ → секция из одной строки «N/A (не затрагивает вход/роли/доступ)» —
явное «нет» вместо молчания (правило честного coverage).

## 4. Инварианты реализации (проверяет stage-2 аудит и code-review)

1. **Flow (OIDC/OAuth 2.0):** Authorization Code (+ **PKCE S256** для public client; public client
   client_secret не отправляет и не логирует). Implicit flow и password grant запрещены.
2. **CSRF/replay:** `state` обязателен и привязан к сессии (httpOnly-cookie); `nonce` + проверка
   подписи, `iss`, `aud` и `exp` ID-токена.
3. **Секреты** (client secret, `SESSION_SECRET`): только env/secret-store, вне репозитория; никогда в
   коде, логах, argv, тикетах, скриншотах. Ротация — по политике владельца/безопасности.
4. **Токены не в localStorage/sessionStorage.** Сессия — на бэкенде, cookie `httpOnly` + `secure` в
   проде + осознанный `SameSite`; фронтенд получает пользователя через серверный endpoint
   (например `/auth/user`), не хранит токены сам.
5. **HTTPS обязателен в проде;** redirect URI — точное совпадение с регистрацией, без wildcard.
6. **Роли только из серверного источника** (группы IdP или собственная таблица ролей): маппинг на
   бэкенде, никаких self-claimed ролей из фронтенда. Деактивация пользователя → ревокация активных
   сессий/refresh-токенов, а не только запрет нового входа.
7. **Собственный логин+пароль (если выбран):** адаптивный хэш паролей (argon2id/bcrypt/scrypt),
   rate-limit/lockout попыток входа, одинаковый ответ на «нет пользователя» и «неверный пароль» (без
   user enumeration), одноразовые reset-токены с коротким TTL, ротация идентификатора сессии при
   входе (защита от session fixation).
8. **Наблюдаемость auth-событий:** failed login, token refresh, group-sync, logout — логируются с
   request_id и без секретов (инвариант наблюдаемости устава, I-9).
9. **Egress-дисциплина интеграций:** каждая интеграция, отправляющая данные наружу (тикеты,
   вебхуки, внешние API), явно объявляет в спеке — ЧТО покидает периметр, КУДА и при каких условиях;
   свободный текст владельца/пользователя во внешнюю систему — только после проверки видимости
   приёмника (публичный репозиторий/канал → явное подтверждение, не молчаливый дефолт).

Env-конвенция (имена — под проект, в репозитории только имена): `AUTH_CLIENT_ID`,
`AUTH_CLIENT_SECRET`, `AUTH_ISSUER_URL` (issuer из `PROJECT.md §6`), `AUTH_CALLBACK_URL`
(`<LIVE_URL>/auth/callback`), `SESSION_SECRET` (случайная строка 32+ байт).

## 5. QA-слой (browser-QA: workflow-qa / visual-qa / ux-route-qa / chaos-qa; e2e: regression-qa)

- **Вход — через видимую форму входа** (правило visible-browser evidence сохраняется) ЛИБО через
  документированный **тест-байпас** (тестовый login-route / тестовый realm IdP): байпас обязан быть
  выключен в prod-конфиге или ограничен тестовыми пользователями `PROJECT.md §5`. Наличие и способ
  байпаса фиксируются в `PROJECT.md §5`.
- **Учётки:** логин — из `PROJECT.md §5`, пароль — из env-переменной, имя которой там указано;
  значение не печатается и не логируется.
- **Rate-limit дисциплина:** не дёргать login-API IdP в цикле — фикстуры/сохранённое состояние сессии
  (токены обновляет только глобальный setup, а не каждый тест).
- **Секрет-дисциплина:** пароли тестовых пользователей, cookies, auth-заголовки не публикуются в
  тикетах, скриншотах и памяти (общее правило `AGENTS.md`).
- **RBAC-проверки:** enforcement-probe обеих сторон — «кнопка спрятана ≠ endpoint запрещён» и
  «кнопка видна ≠ действие разрешено»; для ролей из IdP — смена группы должна менять права после
  re-login (проверка маппинга, не UI).

## 7. Связь с уставом проекта

Инвариант I-7 устава (`docs/constitution.md`) уже ссылается на §3–§4 этого гайда. При заполнении
устава проект с пользовательским входом может конкретизировать I-7 (или поправкой добавить
отдельный инвариант):

> **Auth Governance (MUST).** Вход — по модели `PROJECT.md §6`; роли — только из серверного
> источника; секреты аутентификации — вне репозитория; токены — не в web-storage; для OIDC
> state+nonce+PKCE обязательны; деактивация пользователя ревоцирует сессии; auth-события наблюдаемы
> (request_id). _Как проверить:_ спека содержит «Authentication & Access»; дифф auth-кода проходит
> инварианты `docs/guides/AUTH_GUIDE.md` §4.
