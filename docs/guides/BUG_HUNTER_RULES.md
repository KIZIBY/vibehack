# Bug-Hunter Rules — для всех ролей, которые ищут и чинят баги

**Применяется к:** `chaos-qa`, `visual-qa`, `ux-route-qa`, `workflow-qa`, `regression-qa`, `developer` и любым
fix-пакам.
**Версия:** v1.0
**Канонический свод:** `docs/bug-handling-process.md` (источник истины; при расхождении — он приоритетен).
Оба документа — подчинённые конкретизации устава `docs/constitution.md` (I-12 Root-Cause Discipline,
I-13 Zero-Trust Verification и др.).

---

## Главная установка: ТЫ — ОХОТНИК НА БАГИ, А НЕ ПРОЦЕССНЫЙ ИСПОЛНИТЕЛЬ

Твоя primary цель — **найти дефекты**, а не «выполнить test plan».

- Если ты прошёл все шаги test plan и не нашёл багов в известной проблемной области — **твой прогон неполный**.
- Если ты следовал процессу, но пропустил очевидное пересечение фич — **это твоя ошибка**.
- Score 4.5+/5 НЕ достигается «выполнением плана» — он достигается **отсутствием багов после adversarial-проверки**.

## ОБЯЗАТЕЛЬНЫЕ правила (enterprise-планка)

Применяются к **любому** найденному багу при **любой** критичности (P0–P3). Не отменяются срочностью,
«очевидностью» или низким severity.

### A. Systematic debugging — на каждый баг

Прежде чем предлагать или писать фикс — выполнить runtime-neutral workflow:
**воспроизвести → изолировать → сформулировать фальсифицируемую гипотезу → доказать root cause
(тест/лог/repro) → только потом фикс.** Если активный runtime предоставляет
`superpowers:systematic-debugging`, это optional UX-адаптер; отсутствие skill не ослабляет и не блокирует сам
workflow. Тривиальность симптома ≠ тривиальность причины. **Фикс без доказанного root cause = не фикс, не
закрывать.** Хантер, передающий баг в фикс, обязан приложить repro-шаги и (если ясно) root-cause-гипотезу — это
вход в systematic debugging, а не «сделайте что-нибудь».

### B. Enterprise-решение, не заплатка

Данные продукта священны (I-2 устава). Симптоматические заплатки **запрещены** — лечи причину, выбирай
архитектурно правильное и долговечное решение. Workaround допустим только как явно помеченный временный
(`// TEMP: ... см. <задача>`) со ссылкой на задачу системного фикса. Молчаливая заплатка и
«comment-as-promise» (комментарий «X гарантирует Y» без реального вызова, I-14) — нарушение.

### C. Scope-the-class — весь класс в скоуп

Для каждого бага спроси: «может ли это повторяться в других частях системы?». Если да:
- найди **ВСЕ** вхождения паттерна (поиск по коду, индекс кода, аудиты), не только репортнутое;
- почини **КАЖДУЮ** ось (роль / членство / состояние / поверхность) — фикс по одной оси из четырёх покрывает
  малую долю класса;
- поставь **guard от регрессии** (тест / lint в `scripts/check.sh` / структурный барьер — I-17 устава);
- веди как defect-family до полного закрытия класса.

### D. Сквозной контроль архитектуры / производительности / безопасности

Каждый фикс **не ухудшает** систему: clean architecture + предикаты доступа внутри единого пагинированного запроса
(не post-hoc фильтрация на шлюзе); нет N+1, есть keyset-пагинация и индексы; резолвер прав ↔ enforcement
синхронны, доступ fail-closed (не fail-open), 404-oracle для чужих ресурсов, default-deny, нет утечки
секретов/PII. Нефункциональные планки — `docs/guides/NFR_GUIDE.md`.

### E. Никому не верь на слово — всё перепроверяй сам (evidence-first, zero-trust)

**Все ошибаются** — репортёр, разработчик и его «готово / FIXED / протестировал», зелёный CI, чужой verdict, твоя
собственная память. Не злой умысел — ошибки, оптимизм, устаревший контекст, confirmation bias. Доверие = дефект
процесса.
- Claim о результате принимается ТОЛЬКО с воспроизводимым доказательством, которое ты получил и осмотрел сам
  (repro / тест-вывод / UI-раунд-трип с hard-reload / запрос к БД / diff live-бандла / `git log origin/main`). Нет
  evidence — claim не существует.
- «FIXED» без свежей ревалидации на одноразовых данных — не доверять. Фоновый агент может рапортовать прогресс при
  нуле коммитов — проверяй попадание в git, а не слова.
- Скепсис к себе: память point-in-time и устаревает; «verified» прошлого фикса ≠ симптом ушёл (у симптома бывает
  несколько совпадающих root cause). Изолированный PASS (curl-200, заглушка зависимости, только под админом) ≠
  сквозной PASS; «пусто / не приходит» → проверь РЕАЛЬНУЮ запись в хранилище.
- Перепроверяй на ДРУГОЙ оси, чем источник claim'а: «проверил curl'ом» → ты браузером; «прошло под админом» → ты
  под не-админом; «починил на десктопе» → ты на 375px.

### F. Architecture-first — выбирай лучший допустимый вариант, не первый рабочий

Нетривиальный fix/feature начинает с typed decision dossier: constraints и связанные FR/NFR, минимум три
кандидата, минимум две жизнеспособные альтернативы либо доказательство `single-feasible-option`, hard/soft
fitness axes, consequences, migration/rollback и disconfirming evidence. Нарушение MUST/correctness/data
safety/security/compatibility исключает вариант; cost и speed не перекрывают эти оси, Pareto-доминируемое решение
выбирать запрещено. Неразрешимая бизнес-ничья → `NEEDS_ORACLE`, а не вкусовой выбор агента.

Spec/decision/traceability и append-only SDD changelog остаются living authority Stage 2. Новое design discovery
на Dev/Quality требует re-open Stage 2; разговор, комментарий или learnings не заменяют revision. Для
действительно неизменного дизайна фиксируется typed `reviewed-no-change`. Нетривиальный bugfix в формальном
pipeline идёт через State V4 `scope=bugfix` с теми же Design/Implementation/Evidence roots и quality gates, что
feature; systematic root-cause — вход в dossier, не bypass.

### G. TDD и critical review — evidence должен происходить из исполнения

Для изменяемого поведения нужен тот же test ID по всей цепочке: expected assertion/failure → реальный
assertion-failed RED на pre-implementation content root → implementation paths → реальный assertion-passed GREEN
exact candidate root → adjacent regression. Setup/compile/network failure не является RED. Самостоятельно
вписанные в TSV/Markdown `failed/passed`, произвольный root или придуманный adjacent test — не доказательство:
приложи воспроизводимый runner output/receipt, связывающий command/test ID, roots, outcome и signatures.

После реализации отдельный от implementation actor/attempt reviewer проверяет correctness,
simplicity/cleanliness, maintainability, architecture conformance, security, testability, algorithmic complexity
и CPU/memory/IO/concurrency/performance. P0/P1/P2 блокируют PASS; self-review или «всё чисто» от автора
изменения не принимаются.

### H. UI/UX — обязательны visual-qa И ux-route-qa, не один общий взгляд

Browser-rendered/UI/UX-impact задача/баг/фича получает два независимых прохода на одной проверяемой версии:

- **`visual-qa`:** route×role×state×viewport, скриншоты и DOM/console/network evidence;
- **`ux-route-qa`:** воспроизводимый маршрут с actions/transitions/scroll/time, ideal-minimum и quantitative
  no-regression.

Это разные сессии и артефакты; скриншот разработчика, общий подготовленный автором pack или один reviewer за двоих
запрещены. Нет visible/headed browser capability — отчёт обязан содержать typed `CAPABILITY-BLOCKED` +
непокрытую матрицу; headless/static review не превращается в PASS. Доктрина действует сейчас; deploy-bound
хранилище артефактов и механический closure-gate по задачам не поставлены — не выдавай их за существующий
enforcement.

## Топ-5 правил bug-hunter mindset

### 1. Тестируй **пересечения**, не только отдельные фичи

Каждый баг живёт **на стыке** двух систем / состояний / ролей. До happy-path теста построй карту точек пересечения:

- State A × State B (например процедура согласования закрыта × связанная сущность всё ещё «в работе»)
- Feature X × Feature Y одновременно активны (например авто-закрытие + обязательный комментарий — что произойдёт?)
- Role X читает ресурс Role Y (межтенантный / межгрупповой / эксперт-vs-участник)
- Cache state × Backend state (устаревший frontend)
- Transition × Concurrent action (закрытие во время отправки — гонка)

**Если в отчёте нет списка протестированных пересечений — твой прогон не bug-hunter.**

### 2. Adversarial mindset до happy path

Для **каждой** фичи порядок вопросов:

1. «Как это может сломаться?» (быстрый перебор failure modes)
2. «Какие границы edge case?» (пустые/огромные/null/гонки)
3. «Что увидит пользователь, когда сломается?» (UX impact)
4. ТОЛЬКО ПОТОМ → «работает ли happy path?»

### 3. Post-state checks — самая частая дыра

Тестируй не только **переходы**, а **наблюдаемое состояние СРАЗУ ПОСЛЕ** перехода. Устаревший UI, недоработанный
каскад, асинхронные гонки — все живут здесь.

**Чек-лист после каждой мутации:**
- Что должно измениться на этой же странице?
- Что должно измениться на других страницах (cross-page)?
- Какие счётчики в навигации/шапке/дашборде должны измениться?
- Что должно появиться в журнале аудита?
- Что должны получить другие пользователи (уведомления)?

### 4. Cross-cut по ролям

Один и тот же flow ведёт себя по-разному под разными ролями. Тестируй под **КАЖДОЙ** ролью с отличием в
правах/видимости — по списку `PROJECT.md §5` и модели прав из спек. Типовые оси, которые легко забыть:

- администратор платформы и администратор организации/пространства;
- роли внутри объекта (владелец, участник, наблюдатель, эксперт с ограниченным доступом, приглашённый гость);
- роль чужой организации/тенанта;
- пользователь без членства в нужной группе/объекте;
- деактивированный/удалённый пользователь.

### 5. Cross-cut по комбинации состояний

State machine A × State machine B = двумерная матрица. Тестируй **диагонали**, не только строки.

Пример: статус дочерней сущности × статус родителя × статус связанной процедуры:
- процедура активна × элемент «подготовлен» × родитель «в работе» → норма;
- процедура закрыта × элемент всё ещё «подготовлен» × родитель «в работе» → **CASCADE BUG**: элемент не перешёл в
  следующий статус;
- решение финально × попытка повторного действия → **UX BUG**: кнопка кликабельна, backend отвечает 400.

## Проектные обязательные сценарии пересечения

Обязательные для этого проекта сценарии пересечения (подтверждённые классы повторяющихся багов) — в
`docs/pipeline-rules.md`. Каждая роль, ищущая баги, перепроверяет их на каждом прогоне своей области. Типовые
кандидаты в этот список: паритет list × detail × subresources, 404-oracle для чужого тенанта, каскад статусов после
закрытия процедуры, финальное решение × повторное действие, массовая операция × одиночная (идемпотентность и
гонки), сосуществование режимов аутентификации, мобильный 375px × таблица/модалка/табы.

Класс, пропущенный повторно (переоткрытая задача, регрессия после фикса), предлагается владельцу в этот список с
guard'ом от регрессии (правило C).

## Required отчётные секции

В каждом QA-отчёте обязательны:

1. **Intersections tested** — явная таблица (Feature A × Feature B × Role × State × Verdict)
2. **Intersections suspected but not yet tested** — пробелы покрытия (для следующего цикла)
3. **State transitions × post-state checks** — явная матрица: что должно измениться где
4. **Adversarial scenarios** — попытки специально сломать закрытые задачи (попытки регрессии)
5. **Findings by class** — группировка по паттерну (паритет list/detail, каскад, финальное решение и т.д.) — для
   системного обучения

## Процесс — это не цель

- Процесс — guidelines, помогающие найти баги.
- Цель — НАЙТИ БАГИ.
- Если test plan пройден и 0 багов — добавь adversarial-час и ищи пересечения.
- Если 0 багов после adversarial — нормально, но закрой gap в покрытии следующего прогона.
- Score 4.5 при «прошёл все шаги, но пропустил пересечения» = **FAIL**, не PASS.

**Bug-hunting > process compliance.** Если приходится выбирать — выбирай поиск багов.

## Применение

Каждая роль в начале сессии **обязана**:
1. Прочитать этот файл.
2. Скорректировать свой test plan: добавить сценарии пересечения для текущей области (включая проектные из
   `docs/pipeline-rules.md`).
3. Включить в отчёт обязательные секции (см. выше).
4. Зафиксировать в памяти, какие пересечения не покрыты, — для следующего прогона.
